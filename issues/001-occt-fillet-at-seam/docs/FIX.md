## 3. Где именно принимается решение

Инструментированная сборка `TKFillet` печатает решения по ходу дела
(`CHFI3D_TRACE=1`; без переменной код молчит и ведёт себя как неинструментированный).

### 3.1. Ветка `nba>3` не используется — предыдущая гипотеза здесь не подтверждается

`docs/OCCT_SOURCES.md` §4 указывает на отсутствующий `ChFi3d_Recale` в
`PerformIntersectionAtEnd`. Трасса показывает, что **в этом дефекте та функция не
вызывается вообще**:

```
[CHFI3D] ===== PerformFilletOnVertex Index=1 vertex=(25.000000, 19.347656, 10.000000)
[CHFI3D]   stripes i=1  nba(sharp edges)=3  nondegenere=yes -> PerformOneCorner / PerformMoreSurfdata (nba<=3)
[CHFI3D] ENTER PerformOneCorner Index=1 vertex=(25.000000, 19.347656, 10.000000)
```

`nba = 3`, значит условие `if(nba>3)` в `ChFi3d_Builder.cxx:690` ложно, и
`PerformIntersectionAtEnd` не вызывается ни разу — зонд на её входе не сработал ни на
одном прогоне. Работает `PerformOneCorner`.

**Разбор механизма в `OCCT_SOURCES.md` при этом был верен, ошиблось только место.**
Это тот же самый пропуск `ChFi3d_Recale`, но одной функцией раньше. Пропуск в
`PerformIntersectionAtEnd` тоже реален — он просто латентен для этой детали
(см. §9).

### 3.2. Что решается на строке 807

Один и тот же зонд на хорошем и плохом случае, разница только в положении шва:

```
ХОРОШИЙ (rot=0, шов в 11,514078 мм от вершины):
  onsame=no IFadArc=1 IFopArc=2 inters=yes
  face at end (Bs) = Geom_CylindricalSurface  uperiodic=YES uperiod=6.283185307
  BEFORE recale: pfac1=(4.605818022, 6.707106747) pfac2=(4.818959934, 6.707106780) du=0.213141912
  |du|=0.213141912 <= half period 3.141592654 : no seam jump
  its pcurve on the face at end: u 4.605818027 -> 4.818959933 (span 0.213141906)
  -> RESULT ... status=OK valid=true removed=+1.368076 bop=clean

ПЛОХОЙ (rot=270, шов ровно на вершине):
  onsame=no IFadArc=1 IFopArc=2 inters=yes
  face at end (Bs) = Geom_CylindricalSurface  uperiodic=YES uperiod=6.283185307
  BEFORE recale: pfac1=(6.176614355, 6.707106789) pfac2=(0.106570952, 6.707106787) du=-6.070043403
  *** |du|=6.070043403 > half period 3.141592654 : THE TWO POINTS SIT ON OPPOSITE SIDES
      OF THE SEAM. onsame is FALSE so ChFi3d_Recale is SKIPPED. ***
  its pcurve on the face at end: u 6.176614355 -> 0.106570952 (span 6.070043403)
  -> RESULT ... status=BROKEN_VOLUME_GREW valid=false removed=-374.971265 bop=DIRTY
```

Ключевые факты, каждый измерен:

1. Грань, к которой приходит фаска (`Bs`), — **цилиндрическая и периодическая**,
   период 6,283185307 = 2π. Это и есть грань со швом.
2. `onsame = no`. Статус спайна = 2, то есть **не** `ChFiDS_OnSame`. Значит охрана
   `if (onsame)` на строке 807 **не пускает** `ChFi3d_Recale`.
3. Две точки `pfac1` и `pfac2` — это концы стыковочной кривой на этой грани. В плохом
   случае они лежат **по разные стороны шва**: 6,176614355 и 0,106570952.
4. `|du| = 6,070043403 > π = 3,141592654`, то есть больше полупериода — ровно то
   условие, которое `ChFi3d_Recale` и существует чтобы чинить.

### 3.3. Проверка арифметикой: это одна и та же дуга

```
2π − 6,070043403 = 0,213141904
хорошая дуга      = 0,213141912
```

Совпадают до восьмого знака. **Геометрия в обоих случаях одна и та же**, отличается
только ветвь параметра: в плохом случае та же дуга берётся «в обход» цилиндра.

В миллиметрах, при радиусе кармана 6,647656:

| | дуга, рад | длина стыковочной кривой |
|---|---|---|
| правильная (короткая) | 0,213141904 | **1,416894 мм** |
| построенная (длинная) | 6,070043403 | **40,351560 мм** |

Сорок миллиметров стыковочной кривой на фаску радиусом 1 мм. Отсюда и
«Self-intersecting wire», и рост объёма.

### 3.4. Почему ошибку не ловит ни одна проверка ниже по течению

Параметры `u` и `u+2π` на цилиндре дают **одну и ту же точку в 3D**. Проверка
«достойности входных данных» в начале `ChFi3d_ComputeCurves`
(`ChFi3d_Builder_0.cxx:2952`, сравнение `pdeb1.Distance(pdeb2)`) сравнивает именно
3D-точки и проходит успешно. Ошибка чисто параметрическая и в 3D невидима — это
объяснение уже было дано в `docs/OCCT_SOURCES.md` §4 и оно верное.

## 4. Правка

Полный diff против чистого OCCT 7.8.1 — одна строка кода плюс комментарий:

```diff
--- build/occt-src-orig/ChFi3d_Builder_C1.cxx
+++ C:/dev/occt-fix/src/ChFi3d/ChFi3d_Builder_C1.cxx
@@ -804,7 +804,18 @@
     else {
       pfil2 = Fi2.PCurveOnSurf()->Value(Fi2.Parameter(!isfirst));
     }
-    if (onsame) ChFi3d_Recale(Bs,pfac1,pfac2,(IFadArc == 1));
+    // ------------------------------------------------------------------
+    // seam-fillet fix, 2026-09-12.
+    // pfac1 and pfac2 are two 2d points on the SAME face surface Bs. When that
+    // surface is periodic they can come out on opposite branches of u (u and
+    // u+2pi are the same 3d point, so no downstream check notices), and then
+    // Pardeb/Parfin describe the long way round the cylinder instead of the
+    // short arc. ChFi3d_Recale is the helper that normalises exactly this.
+    // It was called only in the `onsame` case; the seam defect happens with
+    // onsame == false, where it was skipped. IntersectMoreCorner (the sibling
+    // routine) already calls it unconditionally.
+    ChFi3d_Recale(Bs,pfac1,pfac2,(IFadArc == 1));
+    // ------------------------------------------------------------------
```

Почему именно так, а не иначе:

* **Ничего не переписывается.** Убрана охрана, вызов оставлен буква в букву,
  вместе с аргументом `(IFadArc == 1)`.
* **Это не изобретение.** Соседняя процедура `IntersectMoreCorner`
  (`ChFi3d_Builder_C1.cxx:4031` в чистом дереве) зовёт ровно этот вызов с ровно этим
  аргументом **безусловно**. Правка приводит `PerformOneCorner` к тому же виду.
* **`ChFi3d_Recale` сам себя охраняет.** Первое, что он делает, — проверяет
  `IsUPeriodic()`/`IsVPeriodic()` и `fabs(u2-u1) > 0.5*uper`. На непериодической
  поверхности он не трогает ничего. То есть охрана `if (onsame)` была лишней даже
  логически: настоящее условие уже внутри.

### Влияет ли третий аргумент `refon1`

Проверено, а не оставлено на вкус. Собраны и прогнаны обе крайности:

| `refon1` | результат на шве, 4 радиуса |
|---|---|
| `(IFadArc == 1)` — как в оригинале | `+0.085452 / +0.341850 / +1.368076 / +5.483165`, всё clean |
| `Standard_True` | те же числа, всё clean |
| `Standard_False` | те же числа, всё clean |

Разницы нет: обе ветви дают одну и ту же короткую дугу, просто описанную от разного
начала. Оставлено оригинальное выражение — оно минимальнее.

## 6. Проверка, что правка ничего не сломала

### 6.1. Собственные тесты OCCT запустить нельзя — и это надо сказать прямо

Тестовый набор OCCT управляется `DRAWEXE`. `DRAWEXE` — это модуль `Draw`, которому
нужен Tcl/Tk. По `docs/BUILD.md` §2 модуль `Draw` выключен именно потому, что Tcl/Tk на
машине нет. Значит **«прогнать тесты OCCT» здесь недоступно**, и ни одного из них я не
запускал. Вместо этого сделана своя батарея.

### 6.2. Батарея регрессий: 40 случаев, сравнение побайтово

`repro/cpp/fillet_regress.cpp` строит 40 случаев — фаски-скругления, фаски-скосы и
булевы операции на телах со швом и без — и печатает по одной детерминированной строке
на случай (IsDone, `BRepCheck_Analyzer`, объём, число граней и рёбер, `BRepAlgoAPI_Check`).

```
build/regress/fillet_regress.exe            # с чистым ядром на PATH   -> before.txt
build/regress/fillet_regress.exe            # с исправленным ядром     -> after.txt
diff before.txt after.txt
```

```
diff: РАЗНИЦЫ НЕТ ВООБЩЕ (44 строки совпали побайтово)
```

Что внутри батареи: коробка (одно ребро, два, три в углу, все рёбра, r=1/2/3), скосы,
цилиндр (все рёбра, обод r=0,5/2), конус, сквозное отверстие, глухое отверстие,
объединение двух коробок, цилиндрический прилив, **паз поперёк отверстия** (76 граней,
175 рёбер), четыре случая «маленькое отверстие + большая фаска», и шесть булевых
операций (cut/fuse/common на коробках, цилиндрах, сфере, торе). 39 случаев из 40
строятся, один (`smallhole r=2.5 fillet r=4.0`) честно даёт `NOTDONE` — фаска больше,
чем есть материала, — и даёт `NOTDONE` одинаково до и после.

### 6.3. Радиус поражения правки, посчитанный, а не заявленный

Инструментированной сборкой посчитано, сколько раз изменённая строка вообще может
что-то сделать, на всей батарее:

```
PerformOneCorner entries : 26
corner curves computed   : 26
periodic face at end     : 0
seam jump |du|>half per  : 0
onsame=YES occurrences   : 0
```

То есть на 40 случаях `PerformOneCorner` отработал 26 раз, и **ни разу** грань на конце
не была периодической. `ChFi3d_Recale` на непериодической поверхности не меняет ничего
по построению, поэтому совпадение вывода побайтово — не везение, а следствие.

Случай «периодическая грань, но `|du|` маленький» — это строки `rot 0` основной
таблицы: 14 прогонов (4 + 10 радиусов), в которых после правки `ChFi3d_Recale`
действительно вызывается, проверяет условие и ничего не меняет. Вывод там совпал
до последнего знака.

Итого три покрытых класса:

| класс | случаев | результат |
|---|---|---|
| непериодическая грань на конце | 26 стыковок в батарее | вывод побайтово тот же |
| периодическая грань, `|du| < π` | 14 прогонов `rot 0` | числа те же до последнего знака |
| периодическая грань, `|du| > π` | это и есть дефект | было сломано → стало верно |

(«не удалось открыть создаваемый файл») на семи файлах пакета
`IntWalk`/`IntCurveSurface`/`GeomInt`. Причина названа, а не угадана: MSBuild держит
узлы-процессы живыми ради переиспользования, и `Get-Process MSBuild` показывал узлы,
запущенные в 03:06 и 03:29, всё ещё в памяти — они держали файлы моей же убитой
сборки. Это столкновение за файлы, а не дефект кода. Собранные DLL в таком состоянии я
использовать не стал: пересобрал начисто, когда ничего другого не работало, и только
после `0 ошибок` на 365 перекомпилированных файлах считаю ядро годным. Числа §5
измерены и на гибридном рантайме (17 чистых соседей + исправленный `TKFillet`), и на
полностью пересобранном ядре — они совпадают.

Команда:

```
cmake --build C:/dev/freecad-kernel-fixes/build/occt-fix --target TKFillet --config Release \
      -- -m -v:m -p:BuildProjectReferences=false
```

`-p:BuildProjectReferences=false` — чтобы MSBuild не трогал остальные 17 тулкитов;
их `.lib` положены в дерево заранее, они собраны из тех же чистых исходников тем же

перебрать варианты аргумента `refon1` и три варианта гипотезы вместо рассуждений о них.

## 8. Что лежит в итоге и как этим пользоваться

### 8.1. Готовое ядро, на котором можно писать приложение

**`C:/dev/freecad-kernel-fixes/install/occt-fix`** — самодостаточное исправленное ядро:

```

win64/vc14/bin/     18 DLL
win64/vc14/lib/     18 import-библиотек
68 МБ, не зависит ни от чего снаружи себя
```

Это отдельно важно. В `build/occt-fix/inc` (и точно так же в `build/occt-release/inc`,
которое собрала другая команда) лежат **переходники** — файлы в одну строку вида

```
#include "C:/dev/occt-fix/src/ChFi3d/ChFi3d_Builder.hxx"
```

Всё, что собрано против них, перестанет компилироваться в тот день, когда дерево
исходников переедет. В `install/occt-fix/inc` лежат настоящие копии, и этой ловушки там
нет.

Проверено сквозным прогоном, а не заявлено:

```
powershell -File build-scripts/verify-fixed-kernel.ps1
```

компилирует `repro/cpp/seam_fillet.cpp` против `install/occt-fix/inc` и
`install/occt-fix/win64/vc14/lib` (cl EXIT=0, 2,12 с), затем запускает его, поставив в
`PATH` **только** `install/occt-fix/win64/vc14/bin` и `System32`, — то есть никакой
другой копии OCCT загрузиться не может:

```
rot 0   (шов далеко) : removed +1.368076  valid true  bop clean   faces 8 -> 9
rot 270 (шов на вершине): removed +1.368076  valid true  bop clean   faces 8 -> 9
```

Тело строится тремя вызовами `BRepPrimAPI` и одним `BRepAlgoAPI_Cut`, ребро скругляется
`BRepFilletAPI_MakeFillet`. Это ровно то, что требовалось: заголовки, import-библиотеки,
DLL и программа, которая на них собирается, строит тело и скругляет ребро.

**`install/occt-fix` намеренно НЕ в репозитории.** 68 МБ двоичных файлов git-у не нужны,
а `.gitignore` я не трогал — это общий файл, и другая команда правит репозиторий прямо
сейчас. Каталог `install/` поэтому числится неотслеживаемым. Восстанавливается одной
командой: `bash build-scripts/setup-occt-fix.sh`. Если кто-то соберётся добавить
`install/` в `.gitignore` — так и надо сделать, просто не посреди чужой работы.

Наложить и снять правку:

```
python build-scripts/chfi3d_patch.py fix       # только правка
python build-scripts/chfi3d_patch.py trace     # только инструментовка
python build-scripts/chfi3d_patch.py trace fix # и то и другое
python build-scripts/chfi3d_patch.py revert    # вернуть чистый 7.8.1
python build-scripts/chfi3d_patch.py status
```

Скрипт ищет места вставки **по тексту строки внутри именованной функции** и падает,
если совпадение не единственное, — наполовину наложенная правка в файл на 6000 строк
хуже, чем отсутствие правки. Он всегда начинает с эталонной копии, поэтому
`trace` после `fix` не накладывается вторым слоем.

Инструментовка **молчит**, пока не задана переменная `CHFI3D_TRACE`:

```
CHFI3D_TRACE=1 PATH="C:/dev/freecad-kernel-fixes/build/variant/trace:$PATH" \
  build/seam-fillet/seam_fillet.exe --case --rot 270 --radius 1.0
```

## 9. Чего это НЕ доказывает

Список ограничений — не оговорки, а граница утверждения.

1. **Зависание не воспроизведено и не исправлено.** На этой фикстуре зависаний нет
   вообще: самый долгий из всех прогонов — 0,057 с. Измеренные ранее 9,2 минуты на
   реальной детали владельца остаются невоспроизведёнными, и правка к ним отношения
   иметь не обязана. Заметно, что `r=0,55` — один из тех двух радиусов — здесь давал
   порчу, а не зависание, и теперь корректен; но это **не то же самое**, что
   «зависание исправлено». Утверждать этого нельзя.

2. **Через FreeCAD не проверено.** Исходный замер (+356,4531 мм³ роста) сделан в
   FreeCAD 1.1.1. Чтобы повторить его с исправленным ядром, нужно подменить
   `TKFillet.dll` в `C:\Program Files\FreeCAD 1.1\bin` — изменение установленной
   программы владельца, пока он спит. Я этого не делал. Порядок действий, когда он
   решит: переименовать `bin\TKFillet.dll` в `TKFillet.dll.orig`, положить туда
   `build/variant/fixA/TKFillet.dll`, прогнать `repro/python/03_minimal_pair.py`
   в `FreeCADCmd`. Подменить через `PATH` нельзя: Windows ищет DLL рядом с exe
   раньше, чем в `PATH`.

3. **Не найден случай, где длинная дуга законна.** `ChFi3d_Recale` укорачивает дугу
   всегда, когда `|du| > полупериода`. Если бы существовала геометрия, где стыковочная
   кривая обязана обойти цилиндр «в обход», правка сломала бы её. Я такой не построил —
   в батарее есть семейство «маленькое отверстие + большая фаска» именно под это, и там
   грань на конце ни разу не оказалась периодической. Довод, почему такого случая
   скорее всего нет (это **рассуждение, не измерение**): `PerformOneCorner` вызывается
   на конце незамкнутого спайна, стыковочная кривая локальна и по длине сопоставима с
   радиусом фаски; в сломанном случае «длинная» кривая вышла 40,35 мм при фаске 1 мм.
   Замкнутый спайн до угловой обработки не доходит вовсе. Опровергнуть это может
   контрпример, и его стоит поискать.

4. **Комментарий 2002 года не проверен.** В `PerformIntersectionAtEnd` (строки
   2422–2469) закомментирован блок нормализации периода с пометкой *«may cause trimming
   a wrong part of periodic surface»* (occ354, 30 мая 2002). Это **другое** место и
   другая правка; моя к нему не относится, и я не проверял, что там ломалось.

5. **Пропуск `ChFi3d_Recale` в `PerformIntersectionAtEnd` остаётся.** Разбор в
   `docs/OCCT_SOURCES.md` §4 верен по механизму: там вызова действительно нет, тогда
   как в двух соседних процедурах он есть. Для этой детали ветка не используется
   (`nba = 3`), так что дефект там **латентный**. Он должен проявиться на вершине, где
   сходится больше трёх острых рёбер, и грань на конце — цилиндр со швом. Такой
   фикстуры я не построил.

6. **Правка не отправлена в апстрим и не сверена с современной веткой OCCT.** Сделана
   против тега `V7_8_1`. Возможно, в master это уже исправлено иначе.

7. **Совпадение батареи побайтово доказывает отсутствие возмущения, а не отсутствие
   регрессий вообще.** 40 случаев — это 40 случаев, а не тестовый набор OCCT.

## 11. Предупреждение о рабочем дереве `occt/`

`C:/dev/freecad-kernel-fixes/occt` на момент написания содержит чужие правки и мою
инструментовку, попавшую туда до перехода в изолированное дерево
(`git -C occt diff --stat` показывал 101 добавленную строку в двух файлах ChFi3d).
Я его сознательно **не** откатывал. Это проверено, а не предположено: в 03:5x
`Get-Process` показывал живые `cl`, `cmake` и два десятка узлов `MSBuild`, то есть
сборка шла прямо в этот момент. Менять исходники под работающей сборкой — ровно тот
способ получить `C1083`, который описан в §7.

Текущее содержимое `git -C occt diff` — это **только моя инструментовка** (101 строка
добавлена, 0 удалено); чужая правка `if (onsame)` из неё уже убрана самой другой
командой, она ушла работать в своё дерево `C:/dev/occt-e9`.

Моя инструментовка безвредна — она молчит, пока не задана `CHFI3D_TRACE`, — но это
дерево больше не является чистым 7.8.1. Эталон, с которым можно сверяться, лежит в
`build/occt-src-orig`, и он сверен с `git show HEAD:` побайтово. Вернуть дерево к
чистому состоянию можно через `git -C occt checkout -- src/ChFi3d`, **но только
убедившись, что другая команда закончила.**
