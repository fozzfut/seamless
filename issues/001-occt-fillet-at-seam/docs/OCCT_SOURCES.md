то есть ребро принимается как «имеющее две смежные грани» даже когда обе грани —
одна и та же, при условии что ребро замкнуто на ней. Это ровно определение шва:
одно ребро, две pcurve.

## 3. Код, который знает про шов

Все помощники — в `src/ChFi3d/ChFi3d_Builder_0.cxx` (couture по-французски «шов»):

| Функция | Строка | Назначение |
|---|---|---|
| `ChFi3d_Couture` | 4644 | есть ли у грани шов вообще |
| `ChFi3d_CoutureOnVertex` | 4668 | **есть ли у грани шов, один из концов которого — данная вершина** |
| `ChFi3d_IsPseudoSeam` | 4698 | ребро замкнуто, но рядом есть настоящий шов |
| `ChFi3d_NbSharpEdges` | 4554 | считает острые рёбра при вершине |
| `ChFi3d_NumberOfSharpEdges` | 4597 | то же, с поправкой на свободные края |

`ChFi3d_CoutureOnVertex` — это буквально наш случай, «шов кончается на вершине»:

```cpp
// ChFi3d_Builder_0.cxx:4668
void ChFi3d_CoutureOnVertex( const TopoDS_Face & F, const TopoDS_Vertex & V,
                             Standard_Boolean & couture, TopoDS_Edge & edgecouture)
{ ...
  if (BRep_Tool::IsClosed(Ecur,Surf,Loc)) {
    TopoDS_Vertex Vf, Vl;
    TopExp::Vertices( Ecur, Vf, Vl );
    if (Vf.IsSame(V) || Vl.IsSame(V))
    { couture = Standard_True; edgecouture = Ecur; break; }
  }
}
```

Вызывается он ровно там, где спайн фаски приходит в вершину —
`ChFi3d_Builder_C1.cxx:1585–1589`, внутри `PerformIntersectionAtEnd`:

```cpp
for(ItF.Initialize(myVFMap(Vtx));ItF.More()&&!couture;ItF.Next()) {
  TopoDS_Face fcur = TopoDS::Face(ItF.Value());
  ChFi3d_CoutureOnVertex(fcur,Vtx,couture,edgecouture);
  if (couture) facecouture=fcur;
}
```

Дальше найденный `couture` используется всего в трёх местах: подмена соседнего
ребра (строки 1616, 1623), запрет «одного угла» (1667–1668, 1677) и —

```cpp
// ChFi3d_Builder_C1.cxx:1802
if (couture || bordlibre) nface=nface+1;
```

то есть шов просто увеличивает счётчик граней на единицу. Никакой работы с
периодом параметра тут нет.

## 4. Где именно ломается

В `ChFi3d_Builder_C1.cxx` есть функция, которая приводит две 2d-точки на
периодической поверхности к одной ветви параметра — `ChFi3d_Recale`, строка **440**:

```cpp
static void ChFi3d_Recale(BRepAdaptor_Surface& Bs, gp_Pnt2d& p1, gp_Pnt2d& p2,
                          const Standard_Boolean refon1)
{ ...
  if (surf->IsUPeriodic()) {
    Standard_Real u1 = p1.X(), u2 = p2.X();
    Standard_Real uper = surf->UPeriod();
    if (fabs(u2-u1) > 0.5*uper) {
      if (u2<u1 && refon1) u2 += uper;
      else if (u2<u1 && !refon1) u1 -= uper;
      else if (u1<u2 && refon1) u2 -= uper;
      else if (u1<u2 && !refon1) u1 += uper;
    }
    p1.SetX(u1); p2.SetX(u2);
  } ... }
```

Это ровно то лечение, которого требует шов. Три места в файле имеют **одинаковую
структуру** — посчитать `pfac1`/`pfac2`, сложить их в `Pardeb`/`Parfin`, позвать
`ChFi3d_ComputeCurves`. Сравним:

| Функция | `ChFi3d_Recale` | `Pardeb(3)` / `Parfin(3)` | `ChFi3d_ComputeCurves` |
|---|---|---|---|
| `PerformOneCorner` (519) | **807**, под `if (onsame)` | 810 / 812 | 818 |
| `IntersectMoreCorner` (3752) | **4031**, безусловно | 4033 / 4035 | 4040 |
| **`PerformIntersectionAtEnd` (1542)** | **отсутствует** | 2472 / 2474 | 2485 |

`grep -n "ChFi3d_Recale(Bs" ChFi3d_Builder_C1.cxx` даёт 807, 1225, 4031, 4298 —
**ни одной строки в диапазоне 1542–2964**, то есть во всей
`PerformIntersectionAtEnd`.

Вместо неё там стоит закомментированный блок — строки **2422–2469**:

```cpp
    // commented by eap 30 May 2002 occ354
    // the following code may cause trimming a wrong part of periodic surface
...
//     if (couture || Sfacemoins1->IsUPeriodic()) {
//       Standard_Real ufmin,ufmax,vfmin,vfmax;
//       BRepTools::UVBounds(Face[nb-1],ufmin,ufmax,vfmin,vfmax);
//       ...
//       pfac1.SetX(xx1);
//       pfac2.SetX(xx2);
//     }
```

Это была нормализация `u` по периоду именно для шва (`couture`) и для
периодической поверхности. Её отключили 30 мая 2002 года, потому что она
«может обрезать не ту часть периодической поверхности», и **ничем не заменили**.

В результате на строках 2472/2474 в `Pardeb`/`Parfin` попадают сырые значения:

```cpp
    Pardeb(3)= pfac1.X();Pardeb(4) = pfac1.Y();
    Parfin(3)= pfac2.X();Parfin(4) = pfac2.Y();
```

### Почему это не ловится проверками

`ChFi3d_ComputeCurves` (`ChFi3d_Builder_0.cxx:2952`) начинается с проверки
входных данных:

```cpp
  gp_Pnt pdeb2 = S2->Value(Pardeb(3),Pardeb(4));
  gp_Pnt pfin2 = S2->Value(Parfin(3),Parfin(4));
  Standard_Real distrefdeb = pdeb1.Distance(pdeb2);//checks the worthiness
  Standard_Real distreffin = pfin1.Distance(pfin2);//of input data
```

На цилиндре `u` и `u+2π` дают **одну и ту же точку в 3D**. Поэтому проверка
«достойности входных данных» проходит успешно, хотя параметры лежат на разных
ветвях. Ошибка чисто параметрическая и в 3D невидима.

Дальше, если S2 — цилиндр, pcurve принудительно сдвигается так, чтобы её начало
совпало с `Pardeb(3)` (`ChFi3d_Builder_0.cxx:3077`):

```cpp
        if(S2->GetType() == GeomAbs_Cylinder) {
          Standard_Real x,y;
          Pc2->Value(Udeb).Coord(x,y);
          x = Pardeb(3) - x;
          y = Pardeb(4) - y;
          if(Abs(x) >= tol2d || Abs(y) >= tol2d) Pc2->Translate(gp_Vec2d(x,y));
        }
```

То есть ошибка в 2π не отбраковывается, а **впечатывается** в pcurve.

## 5. Измеренное подтверждение механизма

Не рассуждение, а замер. На испорченном результате (см. §7) pcurve рёбер
фасочной грани на цилиндре:

```
cylindrical Face11  u-range=[-0.000000, 6.283185]  span=6.283185 (2pi=6.283185)
   edge2 pcurve BSplineCurve2d u:[6.278621 -> 6.283185]
   edge4 pcurve BSplineCurve2d u:[6.278621 -> 0.045849]   <-- перепрыгивает шов
   edge5 pcurve BSplineCurve2d u:[-0.000000 -> 2.936718]
```

`edge4` начинается при `u=6.278621` (чуть меньше 2π) и кончается при
`u=0.045849` (чуть больше 0). Концы оказались **на разных сторонах шва**, и
никто их не свёл. Кривая идёт «длинным путём» вокруг цилиндра:

```
|u2-u1| = 6.232772 рад       (как построено)
0.5*UPeriod = 3.141593       -> ChFi3d_Recale обязан был сдвинуть
после Recale: u1 -> -0.004564, длина дуги = 0.050413 рад   (правильная короткая дуга)
```

Вместо дуги в 0,050 рад построена дуга в 6,233 рад — отсюда и
«Self-intersecting wire», и рост объёма.

## 6. Следы намерения: известный тяжёлый случай, а не недосмотр

История файла `src/ChFi3d/ChFi3d_Builder_C1.cxx` (через GitHub API; git-история
OCCT начинается только в 2011 году с импорта из SVN, поэтому правка 2002 года в
ней отсутствует — это ограничение, а не вывод).

1. **2002-05-30** — блок нормализации периода в `PerformIntersectionAtEnd`
   закомментирован (`occ354`), комментарий в коде: *«the following code may cause
   trimming a wrong part of periodic surface»*. Отключено и не заменено до сих пор.

2. **2012-05-12**, коммит `84e5bff386`, багтрекер 0023139 — *«BRepFilletAPI_MakeFillet
   algorithm builds edges with wrong first and last parameters: out of pcurve»*.
   jgv добавляет ограничение параметра конца фаски в диапазон pcurve грани (+21 строка).

3. **2012-11-08**, коммит `dbf33db17a` — *«Revert previous integration»*. Правку
   **не удаляют, а заворачивают в `#ifdef OCC23139`**, который нигде не определён.
   Мёртвый код на два с лишним года.

4. **2015-01-15**, коммит `6504f8cd28`, багтрекер 0025657 *«Bad result of Fillet
   operation»*, в сообщении коммита — *«Fix of regression»*. `#ifdef` снимают, но
   добавляют явное исключение:

```cpp
// ChFi3d_Builder_C1.cxx:341-363 (в 7.8.1)
      ////modified by jgv, 10.05.2012 for the bug 23139, 25657////
      Handle(Geom2d_Curve) PConF = fi.PCurveOnFace();
      if (!PConF.IsNull())
      {
        ...
        if (!PConF->IsPeriodic())      // <--- добавлено в 2015
        {
          if (isfirst) { ... parltg = fpar; }
          else         { ... parltg = lpar; }
        }
      }
```

Защита от «параметров вне pcurve» **сознательно не применяется к периодическим
кривым**. Периодический случай — это ровно то, где жила регрессия, и его
вынесли за скобки вместо того, чтобы обработать.

**Вывод.** Это известный тяжёлый случай с намеренным отказом от обработки, а не
незамеченный баг. Два независимых следа: закомментированный блок 2002 года и
исключение `!IsPeriodic()` 2015 года. Ни одной строки «TODO/FIXME» про шов при
этом нет — отказ оформлен молча, через отключение кода.

## 7. Воспроизведение (измерено)

### 7.1. Минимальная пара владельца — перепроверена, воспроизводится

Скрипт прошлого прогона нашёлся в `repro/python/` (`03_minimal_pair.py` +
`seamlib.py`) и был запущен заново. Фикстура: коробка 25 × 25,7184 × 10,
цилиндрический карман R=6,647656, глубина 13, ось наклонена на 45° вокруг Y и
пересекает верхнее переднее ребро коробки в точке (25, 12,7, 10). Фаска r=1,0
ставится на прямое ребро x=25, z=10 длиной 6,370744 мм. Меняется **только**
`AngleXU` профильной окружности — поворот полной окружности вокруг собственной
оси не двигает ни одной её точки.

```
A0.cut(A90).Volume  = 0.000000000000
A90.cut(A0).Volume  = 0.000000000000     -> то же самое множество точек
```

| AngleXU | расстояние шов→ребро | результат |
|---|---|---|
| 0° | **11,514078 мм** | isValid=True, объём 5849,4736 → 5848,1055, снято **+1,3681 мм³** против аналитических **+1,3672**, `check(True)` = clean |
| 90° | **0,000000 мм** | isValid=**False**, объём 5849,4736 → **6205,9267**, то есть объём **вырос на 356,4531 мм³**, `check(True)` = RAISED «Bad orientation of sub-shape» |

Контроль из того же скрипта: **фаска-скос (chamfer)** того же размера на том же
ребре в обоих случаях корректна (снято +3,1885 мм³ против аналитических 3,1854,
check clean). То есть дефект живёт именно в коде фаски-скругления, а не в
булевых операциях и не в топологии тела.

### 7.2. Вторая, независимая фикстура — ширина опасного коридора

Чтобы измерить, насколько близко шов должен подойти, построена своя фикстура:
коробка 20×20×10, сквозной цилиндрический карман R=4 в (10,10),
и неглубокий паз 1,2 мм поперёк верха, который разрезает обод кармана на две
дуги с настоящими концевыми вершинами. Цилиндр перед вычитанием поворачивается
вокруг **своей собственной оси** — тело от этого не меняется, меняется только
положение шва.

Доказательство, что тело одно и то же:

```

vol(ANG=90) = 3482.909052938475
a.cut(b).Volume = 0.000000000000
b.cut(a).Volume = 0.000000000000
```

Фаска r=2,0 на дуге, чья концевая вершина ближе всего к шву
(FreeCADCmd, каждый запуск в своём процессе с `timeout 240`):

| поворот шва | расстояние вершина→шов | результат |
|---|---|---|
| 0° | 0,601704 мм | `StdFail_NotDone` — честный отказ |
| 2° | 0,462389 мм | `StdFail_NotDone` — честный отказ |
| 4° | 0,322933 мм | `StdFail_NotDone` — честный отказ |
| **6°** | **0,183378 мм** | **готово, isValid=False, объём 3543,040388, ΔV = +60,131336, BOP «Self-intersecting wire»** |
| **8°** | **0,043768 мм** | **готово, isValid=False, объём 3543,140738, ΔV = +60,231685, BOP «Self-intersecting wire»** |
| **8,62693°** | **0,000000 мм** | **готово, isValid=False, объём 3502,010222, ΔV = +19,101166, BOP «Self-intersecting wire»** |
| 9°…180° | 0,000000 мм (шов перешёл на соседнюю дугу) | `StdFail_NotDone` — честный отказ |

Ровно тот же почерк, что и на детали владельца: **объём растёт**, `isValid()`
лжёт, BOP-проверка грязная. Опасен именно узкий коридор, где шов подходит к
концевой вершине изнутри дуги: снаружи коридора алгоритм честно отказывается,
внутри — молча возвращает испорченное тело.

Контроль: замкнутый обод (без паза) фаску строит корректно — ΔV = −1,386031 мм³
против аналитических −1,386018 мм³ (теорема Гульдина). Замкнутый спайн не имеет
концевой вершины и до `PerformIntersectionAtEnd` не доходит.

## 8. Программа на C++ (собрана и запущена)

| BOP при расстоянии 0 | грязный | **DIRTY** |

Расстояние и снятый объём совпадают до последнего знака — фикстура
воспроизведена точно. Величина роста объёма отличается (356 против 375), потому
что нулевое расстояние достигается при другой фазе шва: FreeCAD отсчитывает
`AngleXU` от оси X эскиза, а программа — от `XDirection` у `gp_Ax2`. Знак и
порядок величины те же.

**Вывод: дефект в самом OCCT, а не в FreeCAD и не в его Python-обёртке.**

## 9. Чего это не доказывает

- Не снят отладчик: что конкретно этот прогон уходит в `PerformIntersectionAtEnd`
  (ветка `nba>3`), а не в `PerformOneCorner`, **не подтверждено пошагово**.
  Подтверждено косвенно: расхождение возникает только когда шов упирается в
  концевую вершину, и построенная pcurve имеет ровно ту 2π-ошибку, которую
  лечит недостающий `ChFi3d_Recale`. Чтобы закрыть этот зазор, нужен
  отладочный билд OCCT или точка останова — полный debug-билд на 28 ГБ диска
  не поместится, нужен RelWithDebInfo только по TKFillet.
- Правка 2002 года (`occ354`) в git-историю OCCT не входит — она известна только
  по комментарию в коде. Что именно ломалось в `occ354`, проверить нельзя.
- Совпадение «шов упирается в вершину ⇒ 2π-ошибка в pcurve» измерено на фикстуре
  §7.2. На минимальной паре владельца (§7.1) pcurve-замер не повторялся —
  там зафиксированы только валидность, объём и BOP.
- Почему при расстоянии 0 иногда честный отказ (`StdFail_NotDone`), а иногда
  молчаливая порча, из исходников не выведено. Это разные ветки внутри
  `PerformIntersectionAtEnd`, и какая из них выбирается, без отладчика не видно.
- Зависания (измеренные ранее 9,2 мин на детали владельца) на этой фикстуре
  не воспроизвелись: все 17 прогонов уложились в 0,05 с.
