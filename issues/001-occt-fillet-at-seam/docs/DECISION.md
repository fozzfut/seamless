Документ отвечает на центральный вопрос проекта. Все утверждения проверены на
этой машине; рядом с каждым числом стоит команда, которая его получила.

Версия ядра: OCCT 7.8.1, тег `V7_8_1`, коммит `bd2a789f` — тот же, что внутри
FreeCAD 1.1.1. Исходники: `C:/dev/freecad-kernel-fixes/occt`.

## 0. Ответ

**Это ДЕФЕКТ. Одна строка кода. Исправление собрано и измерено — работает.**

Модель данных BRep (шов как обязательное ребро с двумя pcurve) здесь ни при чём.
Ядро умеет обрабатывать этот случай: нужный код написан, лежит в том же файле в

## 1. Механизм, шаг за шагом

### 1.1. Куда попадает вычисление

`src/ChFi3d/ChFi3d_Builder.cxx:690`:

```cpp
if(nba>3) PerformIntersectionAtEnd(Index);
else { if (MoreSurfdata(Index)) PerformMoreSurfdata(Index); else PerformOneCorner(Index); }
```

`nba` считает `ChFi3d_NumberOfSharpEdges` (`ChFi3d_Builder_0.cxx:4597`), которая
через `ChFi3d_NbSharpEdges` (`:4554`) перебирает `myVEMap(Vtx)` и **вычитает**
каждое ребро, у которого соседние грани касательны с точностью G2
(`ChFi3d::IsTangentFaces`, `src/ChFi3d/ChFi3d.cxx`).

Шов цилиндра касателен сам себе: `IsTangentFaces` специально обрабатывает случай
`theFace1.IsSame(theFace2)` — берёт pcurve ребра и pcurve его же в обратной
ориентации (две ветви шва) и сравнивает поверхность саму с собой. Для
аналитического цилиндра это C-бесконечность.

Измерено (`repro/python/10_dispatch_nba.py` воспроизводит логику OCCT на той же
фигуре):

```
AngleXU = 0   VEMap(Vtx).Extent() = 6                              -> nba = 3
AngleXU = 90  VEMap(Vtx).Extent() = 8
   [6] Edge16  F7/F7 SEAM   dNormal=0.00e+00 dCurv=0.00e+00 G2  -> nba--
   [7] Edge16  F7/F7 SEAM   dNormal=0.00e+00 dCurv=0.00e+00 G2  -> nba--
                                                                    -> nba = 3
```

**В обоих случаях `nba = 3`, то есть в `PerformIntersectionAtEnd` вычисление не
уходит никогда.** Шов добавляет два вхождения в карту и тут же вычитается как
касательное ребро. Путь — `PerformOneCorner` (в `MoreSurfdata`, `C1.cxx:3667`,
требуется `nbsurf != 1`, а полоса скругления одного прямого ребра — одна
`SurfData`).

### 1.2. Что именно ломается

`PerformOneCorner` собирает две 2d-точки на грани, в которую упирается скругление
(`Fv` — стенка кармана, цилиндр):

```
C1.cxx:783   pfac1 = BRep_Tool::CurveOnSurface(CV1.Arc(),Fv,...)->Value(CV1.ParameterOnArc());
C1.cxx:790   pfac2 = BRep_Tool::CurveOnSurface(CV2.Arc(),Fv,...)->Value(CV2.ParameterOnArc());
C1.cxx:807   if (onsame) ChFi3d_Recale(Bs,pfac1,pfac2,(IFadArc == 1));   <-- закрыто условием
C1.cxx:814   ChFi3d_Boite(pfac1,pfac2,uu1,uu2,vv1,vv2);
C1.cxx:815   ChFi3d_BoundFac(Bs,uu1,uu2,vv1,vv2);
C1.cxx:818   ChFi3d_ComputeCurves(HGs,HBs,Pardeb,Parfin,Cc,Ps,Pc,...);
```

Измерено (`repro/python/11_pfac_branches.py`) на минимальной паре владельца,
радиус 1.0:

```
AngleXU = 0   (шов в 11.514078 мм)  pfac1.u = 0.570796  pfac2.u = 2.570796  |du| = 2.000000
AngleXU = 90  (шов на вершине)      pfac1.u = 5.283185  pfac2.u = 1.000000  |du| = 4.283185
```

Это **один и тот же телесный угол** — тела доказанно совпадают (взаимное
вычитание даёт 0.000000000000). Отличается только то, на какой ветви шва
оказались точки.

`ChFi3d_Recale` (`C1.cxx:440-470`) существует ровно для этого. Применённая к паре
из второй строки, она даёт:

```
Recale(refon1=True ) -> 5.283185 , 7.283185   дуга = 2.000000 rad
Recale(refon1=False) -> -1.000000 , 1.000000  дуга = 2.000000 rad
```

— **те же 2.000000 rad, что и в рабочем случае.** Без неё в дальнейший расчёт
уходит 4.283185 rad, то есть дуга «в обход», через остальную часть цилиндра.

### 1.3. Почему это фатально

`ChFi3d_Boite` (`ChFi3d_Builder_0.cxx:112`) — это буквально min/max по двум
точкам, а `ChFi3d_BoundFac` то есть `ChFi3d_BoundSrf` (`:493`) **обрезает
поверхность по этому окну** перед пересечением, с запасом
`0.1 * (период - ширина окна)`.

Арифметика (проверена расчётом):

```
без Recale        окно u=[ 1.00000, 5.28318] шир 4.28318 +0.2000 -> [ 0.80000, 5.48319]  вершина внутри: НЕТ
с Recale (False)  окно u=[-1.00000, 1.00000] шир 2.00000 +0.4283 -> [-1.42832, 1.42832]  вершина внутри: ДА
с Recale (True)   окно u=[ 5.28318, 7.28318] шир 2.00000 +0.4283 -> [ 4.85487, 7.71150]  вершина внутри: ДА
```

**Без `ChFi3d_Recale` обрезанный кусок цилиндра не содержит той вершины, к которой
скругление должно примкнуть.** Пересекатель ищет линию стыка на куске поверхности,
где её нет. Отсюда все три наблюдавшихся режима: честный отказ
(`StdFail_NotDone`), молчаливая порча (найден чужой кусок линии) и зависание
(долгий бесплодный численный поиск).

### 1.4. Почему ошибка не отлавливается ниже по течению

`ChFi3d_ComputeCurves` проверяет входные данные так
(`ChFi3d_Builder_0.cxx:2966` и `:2969`):

```cpp
gp_Pnt pdeb2 = S2->Value(Pardeb(3),Pardeb(4));
...
Standard_Real distrefdeb = pdeb1.Distance(pdeb2);  //checks the worthiness
Standard_Real distreffin = pfin1.Distance(pfin2);  //of input data
```

На цилиндре `u` и `u + 2*pi` дают **одну и ту же точку в пространстве**, поэтому
обе проверки проходят. Ветвь параметра для этой проверки принципиально невидима.

### 1.5. Почему фаска на том же ребре того же тела работает

Это было измерено раньше, но не объяснено. Объяснение — в типах поверхностей.
Измерено (`repro/python/12_surface_pair.py`):

```
fillet   новая грань GeomCylinder  площадь 10.028645
chamfer  новая грань GeomPlane     площадь  9.027351
стенка кармана (грань «в конце») = GeomCylinder
```

`ChFi3d_ComputeCurves` имеет аналитические ветви только для цилиндр-на-плоскость
(`:2991`) и плоскость-на-плоскость (`:3090`).

* **Фаска**: плоскость на цилиндр — аналитическая ветвь. Кривая выводится из самих
  квадрик через `IntAna`, границы поверхности не участвуют, а параметры
  нормализуются `ElCLib::AdjustPeriodic(0.,2*M_PI,...)` (`:3065`). Остаточные
  2*pi в pcurve на периодической поверхности геометрически безвредны.
* **Скругление**: цилиндр на цилиндр — аналитической ветви нет, работает численный
  `GeomInt_IntSS` (`:3118`) **по обрезанным поверхностям**. Обрезка неверна, см. 1.3.

Отсюда же видно, что `Pc2->Translate(...)` (`:3077-3082`) сам по себе не виноват:
он лишь доводит pcurve до `Pardeb`, и для фаски это сдвиг на период, то есть
ничего.

### Почему патч безопасен

`ChFi3d_Recale` сама себя ограничивает:

* `C1.cxx:447` — тело работает только `if (surf->IsUPeriodic())`; `:458` — то же
  для V. На непериодической поверхности функция не делает **ничего**.
* `C1.cxx:451`, `:462` — и даже на периодической она правит точки только когда
  `fabs(u2-u1) > 0.5*uper`.

То есть `if (onsame)` охраняет функцию, которая уже охраняет себя сама. Снятие
условия способно изменить поведение исключительно в случае «грань в конце
периодическая И две точки разошлись больше чем на полпериода» — то есть ровно в
сломанном случае. Путь `onsame == true` не затрагивается вовсе: там вызов и так
был.

Прецедент внутри того же файла: `IntersectMoreCorner` (`C1.cxx:3752-4365`)
выполняет структурно тот же расчёт — те же `pfil1/pfil2/pfac1/pfac2`, те же
`Pardeb/Parfin`, тот же `ChFi3d_Boite` и `ChFi3d_BoundFac`, тот же
`ChFi3d_ComputeCurves`, даже то же сообщение об ошибке
`"OneCorner : failed calculation intersection"` — и вызывает `ChFi3d_Recale`
**безусловно** (`C1.cxx:4031`). Слово `onsame` в этой функции не встречается ни
разу.

## 3. Почему это НЕ модель данных

Четыре независимых довода, каждый измерен.

1. **То же тело, тот же шов, другая операция — верный результат.** Фаска того же
   размера на том же ребре корректна при обоих положениях шва: +3.1885 мм3 против
   аналитических 3.1854, `check(True)` чист. Если бы виновата была модель данных,
   фаска ломалась бы вместе со скруглением.

2. **То же тело, тот же алгоритм, другое положение шва — верный результат.** Тела
   при AngleXU 0 и 90 доказанно совпадают (взаимное вычитание 0.000000000000).
   Ничего в форме непредставимо; различается только параметризация.

3. **Ядро умеет это делать — в том же файле.** `IntersectMoreCorner` согласует
   ветви безусловно (`:4031`), а `PerformOneCorner` и `IntersectMoreCorner`
   вдобавок **режут кривую по шву**: находят пересечение с ребром шва через
   `Extrema_ExtCC`, добавляют вершину и создают две кривые вместо одной
   (`C1.cxx:849-868`). Это топологически правильная обработка. Код существует и
   работает.

4. **Патч в одну строку чинит все измеренные радиусы, не трогая остальные
   случаи.** Модельную проблему одной строкой не чинят.

Неоднозначность `u` против `u + 2*pi` действительно встроена в BRep: замкнутая
поверхность параметризуется прямоугольником, и точка на шве имеет два
параметрических образа. Но модель несёт и всё необходимое для разрешения этой
неоднозначности — границы грани в UV, pcurve соседних рёбер, само ребро шва с
двумя pcurve. OCCT этим пользуется в трёх местах из четырёх. Пропуск в четвёртом
— это пропуск, а не предел представления.

## 4. Поправки к более ранним выводам проекта

Прошлый разбор (`docs/OCCT_SOURCES.md`) указал верное семейство функций и верную
роль `ChFi3d_Recale`, но причинная цепочка в нём **неверна**, и это важно, потому
что из неё следовал бы совсем другой патч.

* **Было:** «шов на вершине увеличивает `nba`, поэтому расчёт уходит в
  `PerformIntersectionAtEnd`, где `ChFi3d_Recale` отсутствует».
* **На деле:** диспетчер считает `nba` не через `ChFi3d_conexfaces`, а через
  `ChFi3d_NumberOfSharpEdges` (`ChFi3d_Builder.cxx:683`). Та вычитает касательные
  рёбра, а шов гладкого цилиндра касателен сам себе по G2. Измерено: `nba = 3` и
  со швом на вершине, и без него. **В `PerformIntersectionAtEnd` мы не попадаем.**
* **Следствие:** место сбоя — `PerformOneCorner:807`, а не отсутствие вызова в
  `PerformIntersectionAtEnd`. Патч по прежней гипотезе (раскомментировать блок
  2422-2469) нашу деталь не починил бы.

Отдельно: утверждения о коммитах 2012-2015 годов (`84e5bff386`, `dbf33db17a`,
`6504f8cd28`) **проверить на этой машине нельзя** — клон поверхностный,
`git rev-list --count HEAD` равен 1. Что проверяется и подтверждено: внутрикодовые
комментарии `// commented by eap 30 May 2002 occ354` (`C1.cxx:2422`) и
`//modified by jgv, 10.05.2012 for the bug 23139, 25657` (`C1.cxx:340`), а также
то, что восстановленное ограничение параметров обёрнуто в
`if (!PConF->IsPeriodic())` (`C1.cxx:348`), то есть периодический случай выведен
из-под него явно.

## 6. Что стоило бы изменение модели данных (для сравнения)

Ответ — «дефект», поэтому менять модель не нужно. Но цифру стоит знать, потому
что вариант «сделаем ядро без швов» всплывёт снова. Список того, что читает шов,
и есть цена (`grep -rE ... --include=*.cxx --include=*.hxx src/`):

ShapeExtend ShapeFix ShapeUpgrade StdPrs TopOpeBRep TopOpeBRepBuild TopOpeBRepDS
TopOpeBRepTool TopoDSToStep` и другие.

Иначе говоря: убрать шов из модели — значит тронуть булевы операции, проверку,
сетку, смещение, чтение и запись STEP и IGES и всю геометрию заодно. Против
одной строки.

Напомню измеренный обходной путь (`repro/python/05_removing_the_seam.py`): если
профиль окружности разбить на дуги и выключить `Refine`, шва в теле нет, и
скругление даёт правильные +1.3681. Это остаётся рабочим приёмом для конкретной
детали, но не заменяет исправления и держится только пока никто не включит
`Refine` ниже по дереву.

## 7. Что это значит для варианта «писать своё ядро»

Без энтузиазма в обе стороны.

**Против своего ядра.** Дефект, из-за которого затеян проект, оказался одной
строкой в функции на тысячу строк, и его удалось найти, исправить и проверить за
одну сессию, имея только исходники и 15-секундный цикл сборки. Это довод в пользу
того, что OCCT — работающая база, а не яма: код читаем, функции сравнимы между
собой (именно сравнение четырёх угловых функций и дало ответ), сборка на этой
машине быстрая. Объём, который пришлось бы повторить с нуля, виден из таблицы в
разделе 6.

**За своё ядро.** Найденное не красит ядро. Проверка входных данных в
`ChFi3d_ComputeCurves` (`:2966`, `:2969`) сравнивает 3d-точки и поэтому конструктивно
неспособна заметить ошибку ветви параметра. Ключевой блок согласования отключён
комментарием с 2002 года и не заменён ничем. Ядро возвращает `IsDone = done` и
`Valid = yes` на теле, где снято вдвое меньше нужного (радиус 0.25), и объём
−401 822 998 мм3 на соседнем радиусе. `isValid()` не ловит ничего из этого. Одна
и та же операция уходит в четыре разные функции с четырьмя разными уровнями
аккуратности в обработке шва — это не случайность, а накопленная история.

**Трезвая середина.** Данные этой сессии не поддерживают решение «писать своё
ядро» — они поддерживают решение «держать свою сборку OCCT с набором патчей».
Инфраструктура для этого уже собрана и измерена: клон, конфигурация, сборка за
6 минут, цикл правки за 12 секунд, репро на C++, воспроизводящее дефект без
FreeCAD. Стоимость первого патча — одна строка. Стоимость своего ядра — таблица
из раздела 6, умноженная на всё остальное. Вопрос о своём ядре стоит пересмотреть,
когда накопится не один патч, а десяток, и станет видно, чинятся ли дефекты по
одной строке или каждый требует переписывать подсистему.

## 8. Следующие три шага

Каждый — конкретное действие с проверяемым результатом.

**Шаг 1. Прогнать регрессионный набор OCCT по скруглениям на патче.**
Одна строка на минимальной паре — доказательство диагноза, но не доказательство
безопасности. В `occt/tests/` есть группы `bugs/modalg_*` и группы по
скруглениям и фаскам. Нужен `DRAWEXE`, которого в текущей конфигурации нет
(`BUILD_MODULE_Draw:BOOL=OFF`). Действие: пересобрать с модулем `Draw`, прогнать
тесты на стоке и на патче, сравнить.
Проверяемый результат: список тестов, чей статус изменился. Ожидание — пустой;
если нет, патч уточняется до условия «грань периодическая» вместо безусловного.
Оценка по измеренному: полная сборка 6 минут, `Draw` добавит модуль — считать
надо, не гадать.

**Шаг 2. Проверить патч на реальной детали владельца.**
Сейчас доказательство получено на минимальной паре в чистом OCCT. Реальная деталь
(`part with fillet.FCStd`, Edge9) проверялась только через FreeCAD, то есть против
стоковых DLL. Действие: перенести фикстуру Edge9 в репро на C++ либо подменить
`TKFillet.dll` у копии FreeCAD и прогнать `07_user_part_fillet.py` на радиусах
0.10 / 0.25 / 0.45 / 0.50 / 0.55 / 0.60 / 0.75 / 1.00 под таймаутом.
Проверяемый результат: исчезает ли зависание на 0.5 и 0.55 и совпадают ли снятые
объёмы с аналитикой. Это прямой ответ на исходный вопрос владельца.

**Шаг 3. Закрыть два оставшихся пробела в объяснении.**
(а) Полоса молчаливой порчи 93-96 градусов и честных отказов 84-92 градуса на
второй фикстуре проверена только на стоке; нужно прогнать ту же развёртку на
патче и убедиться, что исчезают обе.
(б) Зависание на 9.2 минуты объяснено только правдоподобно (бесплодный численный
поиск на неверно обрезанной поверхности) — его надо либо воспроизвести на патче и
показать, что оно ушло, либо измерить отдельно.
Проверяемый результат: развёртка по углам с шагом 1 градус на патче — без строк
`DIRTY`, без `NOT DONE` и без превышений таймаута.

## 9. Что НЕ измерено

Честный список. Ничего из перечисленного в выводах выше не используется.

1. **Регрессии.** Прогнано только репро минимальной пары: 11 углов на 6 радиусов.
   Собственный тестовый набор OCCT не запускался. Патч логически безопасен
   (раздел 2), но это рассуждение, а не прогон.
2. **Реальная деталь владельца на патче.** См. шаг 2. Всё, что сказано про
   зависание на 0.5 и 0.55, относится к стоковым DLL внутри FreeCAD.
3. **Отладчик.** Ни одна точка останова не ставилась. То, что путь идёт в
   `PerformOneCorner`, а не в `PerformMoreSurfdata`, выведено из исходников
   (`MoreSurfdata` требует `nbsurf != 1`) и не инструментировано. На вывод это не
   влияет: в `PerformMoreSurfdata` согласования ветвей нет вовсе, поэтому диагноз
   «согласование не выполнилось» верен для обеих веток. Что `onsame` было ложным,
   доказано экспериментом: патч изменил поведение.
4. **Расчёт `nba`** воспроизведён на Python по исходникам, а не снят с работающего
   ядра. Критерий касательности у меня жёстче, чем у OCCT (1e-7 против допусков
   `LocalAnalysis_SurfaceContinuity` порядка 1e-3), то есть OCCT признает шов
   касательным тем более. Направление вывода устойчиво.
5. **История изменений** 2002 и 2012-2015 годов: клон поверхностный, коммиты не
   проверяемы. Подтверждены только комментарии в коде.
6. **Сферы и торы.** Швы посчитаны (3 и 2), скругления у их швов не запускались.
   Патч трогает общий путь, но проверен только на цилиндре.
7. **Ветвление внутри полосы отказа** — почему при расстоянии 0 иногда честный
   `StdFail_NotDone`, а иногда молчаливая порча. Раздел 1.3 даёт общую причину
   (окно обрезки не содержит вершину), но выбор между «линия не нашлась» и
   «нашлась не та» не прослежен.
8. **Влияние патча на `PerformIntersectionAtEnd`** — никакого, функция не
   изменена. Её собственный пробел (нет ни согласования, ни разреза по шву,
   см. таблицу в разделе 2) остаётся открытым и проявится на вершинах, где
   сходятся больше трёх острых рёбер. Нашей детали это не касается.
