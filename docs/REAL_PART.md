# Реальная деталь владельца: скругляется ли Edge9 после патча

Документ отвечает на первый вопрос, который владелец задаст о патче:
**«Edge9 теперь скругляется?»**

Дата измерений: 12 сентября 2026 года.
Рядом с каждым числом — команда, которая его получила. Ни одно число здесь не
перенесено из прошлых документов: всё измерено заново, на двух ядрах, собранных
в один заход и отличающихся ровно одной строкой.

---

## 0. Ответ

**Да. Edge9 скругляется — на всех семи измеренных радиусах, включая те два, на
которых ядро раньше не возвращалось вообще.**

На радиусе 1.0 результат отличается от идеального (аналитического) на
**0.000903 мм3** — это 0.066 % от снимаемого объёма и 1.7e-8 от объёма детали.

| | сток | патч | идеал |
|---|---|---|---|
| объём при r = 1.0 | 6053.913015 | **5455.212690** | 5455.213593 |
| изменение объёма | **+597.332276** (скругление ДОБАВИЛО материал) | −1.368049 | −1.367147 |
| `isValid` | false | **true** | — |
| `BRepAlgoAPI_Check` | DIRTY: NotValid x1, SelfIntersect x107, TooSmallEdge x10 | **clean** | — |
| r = 0.5 и r = 0.55 | **НЕ ВЕРНУЛОСЬ** (304.6 с и 301.8 с, убито по дедлайну) | **0.195 с и 0.194 с**, обе clean | — |

Полоса зависания исчезла. Тихий отказ на r = 0.25 (`isValid = true`, а снято
вчетверо меньше нужного) исчез. Рост объёма исчез.

## 1. Какой дорогой пошло измерение и почему

Было два пути.

**(b) Скопировать установку FreeCAD в рабочий каталог, положить туда патченый
`TKFillet.dll` и прогнать `repro/python/07_user_part_fillet.py`.**
Цена измерена: `C:\Program Files\FreeCAD 1.1` — 2104 МБ, 30 405 файлов; на диске
свободно 28,38 ГБ (`Get-PSDrive C`). Копия нужна отдельная для каждого из двух
ядер, иначе сравнение нечестное. Кроме дискового расхода этот путь оставляет
внутри измерения весь слой FreeCAD: `PartDesign::Fillet` сам собирает аргументы,
есть обёртка `TopoShape`, есть healing.

**(a) Перенести случай Edge9 в чистый C++ против собранного ядра.** Форма
выгружается из документа владельца ровно один раз, в BREP, и дальше читается
программой в 300 строк, которая вызывает `BRepFilletAPI_MakeFillet` напрямую.

**Выбран путь (a).** Он дешевле (ни одной копии FreeCAD), и он строже: слой
FreeCAD из измерения исчезает совсем. Проверка, что от перехода ничего не
потерялось, — в разделе 2.

`repro/python/13_export_user_part.py` копирует `.FCStd` в рабочий каталог и
открывает **копию**; оригинал не открывается никогда.

```

```

Объём после обхода через BREP отличается на `3.6e-12` мм3 — это уровень
округления, а не потеря. Тело, которое считает C++, — то же самое тело.

Та же форма, прочитанная уже программой на C++ (`--probe`):

```
  base solid: volume 5456.580740  faces 11  edges 28  valid true  BOP clean
  edges = 28, faces = 11, seam edges = 1
  edge  3  len  9.000000  (24.999945, 19.347782, 10.000000) -> (18.635984, 19.347782, 3.636039)  SEAM
  edge  9  len  6.370619  (24.999945, 19.347782, 10.000000) -> (24.999945, 25.718401, 10.000000)
```

Ребро ищется **по измеренным концам, а не по номеру**: «Edge9» — имя из FreeCAD,
и совпадение нумерации с картой рёбер OCCT никем не обещано. Программа требует,
чтобы совпадение было единственным, и отказывается работать иначе
(`FindEdgeByEnds`, `edge9_fillet.cpp`). Здесь оно совпало: индекс 9 в карте OCCT
— то же ребро. Шов (`edge 3`) начинается в той же вершине
`(24.999945, 19.347782, 10.000000)`, что и скругляемое ребро: расстояние
`0.000000000` мм.

## 3. Гигиена сравнения: два ядра, одна строка разницы

Ни одно из уже существовавших на машине деревьев не годилось:

* `C:/dev/seamless/occt` — общий клон, его `src/ChFi3d` правит другая команда
  агентов (`git status` показывает оба файла как `M`);
* `C:/dev/occt-fix` — приватное дерево той команды. Пока это измерение
  готовилось, там шла их сборка (13 процессов `cl.exe`, `Get-Process`), и
  `TKFillet.dll` в их каталоге `bin` поменялся прямо под копированием.

Поэтому исходники взяты прямо из тега, в отдельное дерево:

## 4. Таблица

Каждый радиус — **отдельный процесс со своим дедлайном 300 с**
(`repro/cpp/run_edge9.sh`). Процесс, убитый дедлайном, — это результат `TIMEOUT`,
а не сбой измерения: именно «ядро не вернулось» и надо было измерить.

База: `5456.580740` мм3. «Изменение объёма» = объём результата минус база;
**положительное изменение означает, что скругление добавило материал, чего
скругление делать не может.**

### 4.3. Насколько результат близок к идеальному

Идеал — объём базы минус аналитический уголок `(1 − pi/4) * r^2 * L`,
где `L = 6.370619` мм:

| r, мм | идеал, мм3 | измерено (патч), мм3 | разница, мм3 | разница / снятый объём |
|---|---|---|---|---|
| 0.10 | 5456.567069 | 5456.567068 | −0.000001 | 0.0039 % |
| 0.25 | 5456.495293 | 5456.495289 | −0.000004 | 0.0051 % |
| 0.45 | 5456.303893 | 5456.303855 | −0.000038 | 0.0137 % |
| 0.50 | 5456.238953 | 5456.238896 | −0.000057 | 0.0168 % |
| 0.55 | 5456.167178 | 5456.167095 | −0.000083 | 0.0201 % |
| **1.00** | **5455.213593** | **5455.212690** | **−0.000903** | **0.0661 %** |
| 2.00 | 5451.112154 | 5451.097682 | −0.014472 | 0.2646 % |

Разница отрицательная и растёт с радиусом — так и должно быть: аналитическая
формула считает уголок между двумя перпендикулярными плоскостями по всей длине
ребра, а у этого ребра один конец упирается в цилиндрическую стенку кармана, и
там снимается чуть больше. Тот же порядок (0.07 % при r = 1.0) был измерен на
минимальной паре в `docs/DECISION.md`.

### 4.4. Проверка чужими руками: то же самое глазами FreeCAD

`repro/cpp/edge9_fillet.exe --out` сохранил оба результата при r = 1.0 в BREP,
после чего их прочитал **FreeCAD на своих собственных, непатченых DLL**
(`repro/python/14_verify_edge9_result.py`):

```
  base (as exported)         faces = 11  edges = 28  solids = 1  isValid = True  volume =    5456.580614
  r = 1.0, STOCK kernel      faces = 12  edges = 30  solids = 1  isValid = False volume =    6053.912936
                             check(True) = RAISED Bad orientation of sub-shape x1, No error x2
  r = 1.0, PATCHED kernel    faces = 12  edges = 32  solids = 1  isValid = True  volume =    5455.212548
                             delta vs base = -1.368192   distance from ideal = -0.001045   check(True) = clean
```

Стоковое ядро FreeCAD, глядя на тело, построенное патченым ядром, признаёт его
корректным. Обратное неверно: на своём собственном результате оно спотыкается.

Заодно видно, чего стоковому результату не хватало: **30 рёбер против 32**. При
правильном скруглении новая цилиндрическая грань замыкается четырьмя рёбрами на
каждом конце; у стокового результата двух рёбер нет — это и есть та стыковка в
углу, которую не смог построить пересекатель на неверно обрезанной поверхности
(`docs/DECISION.md`, раздел 1.3).

### 4.5. Сходимость со старыми измерениями через FreeCAD

Стоковые числа этого документа получены на другом ядре (собранном здесь) и по
другому пути (без FreeCAD), поэтому их совпадение со старой таблицей
`docs/MEASUREMENTS.md` 5.3 — независимая проверка обоих измерений:

| 0.10 | −142.2981 | −142.297918 | да |
| 0.25 | 5456.5584 | 5456.558518 | да |
| 0.45 | 4599.7393 | 4595.280606 | **нет, расхождение 4.46 мм3** |

Расхождение на r = 0.45 честно оставлено как есть: оба числа получены на
сломанном ядре, оба тела `isValid = false` и BOP-грязные, и совпадения мусора с
мусором никто не обещал. На всех радиусах, где результат воспроизводим, числа
сходятся до четвёртого знака.

## 5. Чего этот документ НЕ доказывает

* Измерение сделано **на одной детали и одном ребре**. Что патч не ломает другие
  случаи — измерено отдельно и не здесь: на стенде из `docs/DECISION.md` десять
  строк развёртки, где шов далеко от ребра, после патча совпадают со стоком
  побайтово. Полного прогона тестов OCCT никто не делал.
* Скругление вызывалось **напрямую** через `BRepFilletAPI_MakeFillet`.
  Что `PartDesign::Fillet` на патченом ядре даст ровно это же, здесь не
  проверялось: для этого нужна копия установки FreeCAD с подменённой DLL
  (путь (b) из раздела 1), а это отдельная работа на 2.1 ГБ диска.
* Время работы измерялось на машине, где **параллельно шла чужая сборка** (13
  процессов `cl.exe`), поэтому времена в таблице — верхние оценки. На вывод это
  не влияет: различие между «0.19 с» и «не вернулось за 300 с» никакой нагрузкой
  не объясняется.

## 6. Как повторить

```bash
# 1. выгрузить деталь (один раз; оригинал не открывается)
"C:/Program Files/FreeCAD 1.1/bin/FreeCADCmd.exe" repro/python/13_export_user_part.py

# 2. приватное дерево исходников из тега
cd C:/dev/seamless/occt && git archive V7_8_1 | tar -x -C C:/dev/occt-e9

# 3. конфигурация и сборка стокового ядра
powershell -NoProfile -ExecutionPolicy Bypass -File build-scripts/configure-occt-e9.ps1
cmake --build C:/dev/seamless/build/occt-e9 --config Release --target TKFillet
cp build/occt-e9/win64/vc14/bin/*.dll build/kernel-e9-stock/

# 4. патч и пересборка одного TKFillet
bash build-scripts/patch-edge9-kernel.sh apply
cmake --build C:/dev/seamless/build/occt-e9 --config Release --target TKFillet
cp build/occt-e9/win64/vc14/bin/*.dll build/kernel-e9-fix/

# 5. программа (собирается один раз, на оба ядра)
powershell -NoProfile -ExecutionPolicy Bypass -File build-scripts/build-edge9.ps1

# 6. две развёртки, каждый радиус — свой процесс со своим дедлайном
bash repro/cpp/run_edge9.sh C:/dev/seamless/build/kernel-e9-stock stock   300
bash repro/cpp/run_edge9.sh C:/dev/seamless/build/kernel-e9-fix   patched 300
```
