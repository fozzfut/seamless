# Вердикт: что готово, чем можно пользоваться и что ставить нельзя

Дата: 12 сентября 2026, утро. Документ написан последним и отвечает на вопрос
владельца: **«есть ли ядро, на котором можно начинать своё приложение, и нет ли
красного?»**

Рядом с каждым утверждением — команда, которая его дала. Числа, взятые из
прежних документов, помечены ссылкой на документ; всё остальное измерено при
написании этого вердикта.

> **Обновление от ночи 12 сентября.** Пункт «патч ставить нельзя» закрыт:
> охрана переписана, доказана и регрессий больше не даёт. Полный прогон —
> `docs/PATCH_V2.md`. Разделы 0, 1, 6 и 7 ниже приведены в соответствие;
> остальное (SDK, стенд, разбор механизма) осталось верным как было.

---

## 0. Ответ в трёх строках

1. **Красного больше нет.** Тупой патч ломал два случая собственного набора
   OCCT; сужённая охрана (`patches/0002-…`) не меняет в наборе `blend` ни одной
   цифры: 475 журналов случаев из 475 совпали со стоком байт в байт, обе
   регрессии исчезли (`docs/PATCH_V2.md`).
2. **Зелёное тоже есть, и его много:** собрано, проверено и лежит на диске
   полноценное стоковое ядро OCCT 7.8.1 (то же, что внутри FreeCAD 1.1.1) с
   заголовками и import-библиотеками — на нём можно начинать своё приложение
   сегодня. Проверено прямо сейчас: программа компилируется за 1,6 с и считает
   объёмы с относительной ошибкой 3,353e-16.
3. **Дефект шва разобран до одной строки и исправлен.** На реальной детали
   владельца исправление работает на всех семи радиусах и даёт ровно те же
   числа, что и тупой патч, — знак в знак. Разделяющий признак найден: не
   периодичность базовой поверхности, а **замкнутость самой грани**
   (`Bs.IsUClosed() || Bs.IsVClosed()`).

Одной фразой: **ядро для разработки — да. Патч ядра — тоже да, с двумя честно
названными дырами в покрытии (`docs/PATCH_V2.md`, раздел 8).**

Строго: одна деталь — это диагноз, прогон набора тестов — это доказательство.
У нас есть и то и другое, и **на версии v2 они сходятся**.

| что измерено (прогон ночи 12 сентября, `docs/PATCH_V2.md`) | сужённый патч `0002` |
|---|---|
| деталь владельца, Edge9, 7 радиусов | 7 из 7 валидны и BOP-clean; на r = 1.0 объём 5455.212690 при идеале 5455.213593 |
| те же 7 радиусов против тупого патча | совпали посимвольно, 7 `RESULT`-строк из 7 |
| набор OCCT, группа `blend` | 0 изменений статуса, **475 журналов из 475 байт в байт как сток** |
| `blend/simple/H4`, `blend/buildevol/D6` | Mass 426531 и 426060, `valid` — как на стоке; регрессий нет |
| своя группа, 247 случаев | 247 OK, журналы байт в байт |
| группы `feat`, `offset`, `chamfer` вдобавок к `blend` | 1096 исполненных случаев всего, изменений статуса 0; единственное разошедшееся сравнение — шум самого набора, воспроизведён на стоке |
| контроль: тупой патч в том же стенде | обе регрессии на месте — стенд не слеп |
| каждый набор прогнан дважды | байт в байт сам с собой |

Ниже — история вопроса: почему **первая** версия патча (`0001`) была признана
непригодной. Разбор остаётся верным и именно он подсказал условие v2.

### 1.1. Почему был забракован тупой патч (версия `0001`)

| что измерено | результат | где |
|---|---|---|
| реальная деталь владельца, ребро Edge9, 7 радиусов | сток: 5 невалидных/грязных тел и 2 невозврата за 300 с; патч: **7 из 7** валидны и BOP-clean за 0,19–0,27 с | `docs/REAL_PART.md` |
| собственный набор OCCT, группа `blend`, 183 исполненных случая | **2 случая OK → FAILED (bad shape)**, улучшений 0 | `docs/REGRESSION.md` |
| свой сгенерированный набор, 247 случаев | 247 из 247 логов побайтово одинаковы | `docs/REGRESSION.md` |

Два сломанных случая — `blend/simple/H4` и `blend/buildevol/D6`. Проверено мной
в исходном дереве: это одна и та же геометрия.

```
$ cat occt/tests/blend/simple/H4
ellipse w1 0 0 0 15 10
mkedge w1 w1 0 pi/2
trotate w1 0 0 0 1 0 0 90
polyline w2 0 0 10 0 0 -10 25 0 -10 15 0 0
wire w w1 w2
mkplane w w
revol s w 0 0 0 0 0 1 270          <-- тело вращения на 270 градусов
tscale s 0 0 0 SCALE1
explode s E
blend result s 1*SCALE1 s_10
checkprops result -s 426548
```

Патченое ядро отдаёт там не «другой правильный», а **невалидный** результат:
`BRepCheck_UnorientableShape` + `BRepCheck_NotClosed` (площадь 426531 → 426419
в H4 и 426060 → 425937 в D6).

Механизм я проверил по исходнику сам — `build/occt-src-orig/ChFi3d_Builder_C1.cxx`,
строки 440–470 (файл сверен с тегом, md5 `908581eb…`):

```cpp
static void ChFi3d_Recale(BRepAdaptor_Surface& Bs, gp_Pnt2d& p1, gp_Pnt2d& p2, ...)
{
  Handle(Geom_Surface) surf = Bs.ChangeSurface().Surface();
  ... ts = DownCast<Geom_RectangularTrimmedSurface>(surf);
  if (!ts.IsNull()) surf = ts->BasisSurface();     // обрезка снимается
  if (surf->IsUPeriodic()) {
    Standard_Real uper = surf->UPeriod();
    if (fabs(u2-u1) > 0.5*uper) { ... сдвиг на период ... }
```

Периодичность проверяется у **базовой** поверхности, а не у грани, и порог —
полпериода. Грань в 270° (ширина 1,5π при периоде 2π) законно держит две точки
дальше чем на π друг от друга — и патч сдвигает одну из них на целый период за
пределы реальной грани. Поэтому снятие охраны `if (onsame)` — **не** no-op вне
шва, вопреки аргументу в `docs/DECISION.md`, раздел 2.

Вывод по версии `0001`: **не пригодна**. Не потому, что не чинит — чинит, и
убедительно. А потому, что чинит слишком широко.

**Именно это наблюдение и дало условие v2:** если беда в том, что проверяется
периодичность базовой поверхности «после снятия обрезки», то спрашивать надо про
обрезку — замкнута ли сама грань по периоду. Инструментированное стоковое ядро
показало, что этот признак разделяет три угла начисто: у детали владельца
`Bs.IsUClosed() = 1` (грань занимает ровно период, два ребра-шва), у H4 и D6 —
`0` (три четверти периода, швов нет), тогда как `IsUPeriodic` равно 1 во всех
трёх. Таблица целиком — `docs/PATCH_V2.md`, раздел 1.

**Как компилировать своё приложение** — одна команда, без `vcvars64.bat` и без
открытия окон (полный скрипт: `build-scripts/build-kernel-smoke.ps1`, пример

```

   /IC:\dev\seamless\build\occt-release\inc ^
   my_app.cpp ^
   /link /LIBPATH:C:\dev\seamless\build\occt-release\win64\vc14\lib ^
   TKernel.lib TKMath.lib TKG2d.lib TKG3d.lib TKGeomBase.lib TKGeomAlgo.lib ^
   TKBRep.lib TKTopAlgo.lib TKPrim.lib TKBO.lib TKBool.lib TKShHealing.lib ^
   TKFillet.lib TKOffset.lib TKFeat.lib TKMesh.lib TKXMesh.lib TKHLR.lib
```

Три обязательных условия, каждое проверено на этой машине:

* `/MD` — Release-сборка OCCT линкуется с динамическим CRT; со статическим
  ломается ловля исключений OCCT (шапка `build-scripts/build-edge9.ps1`);
* в `PATH` при запуске — `build/occt-release/win64/vc14/bin`;
* компилятор — MSVC 14.36 из
  `C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Tools\MSVC\14.36.32532`.

В том же дереве собран `DRAWEXE.exe` — штатная оболочка OCCT; без неё


Это диагностическая трассировка (`CHFI3D_TRACE`, молчит без переменной

## 3. Что теперь работает, чего не работало

### 3.1. Конкретно: Edge9 владельца

Деталь `part with fillet.FCStd`, ребро длиной 6,370619 мм, конец которого лежит
**точно на шве** цилиндрической стенки кармана (расстояние 0,000000000 мм).
Полная таблица — `docs/REAL_PART.md`, раздел 4; здесь сжато:

| r, мм | сток | патч |
|---|---|---|
| 0,10 | `isValid=false`, объём **−142,3** мм³ (от детали ничего не осталось), BOP DIRTY | valid, clean, снято 0,013672 при идеальных 0,013671 |
| 0,25 | `isValid=true` — и при этом снято 0,022 вместо 0,085 (**тихий брак**), BOP DIRTY | valid, clean, снято 0,085450 |
| 0,45 | `isValid=false`, BOP DIRTY | valid, clean |
| 0,50 | **не вернулось за 304,6 с** | valid, clean, 0,195 с |
| 0,55 | **не вернулось за 301,8 с** | valid, clean, 0,194 с |
| 1,00 | `isValid=false`, объём **вырос** на 597,33 мм³ | valid, clean, снято 1,368049 при идеальных 1,367147 |
| 2,00 | `isValid=false`, объём вырос на 578,01 мм³ | valid, clean |

Перекрёстная проверка чужими руками: FreeCAD на **своих собственных непатченых**
DLL читает результат патченого ядра и признаёт его валидным и чистым
(`check(True)` = clean), а на результате стокового ядра спотыкается
(`Bad orientation of sub-shape`). Скрипт: `repro/python/14_verify_edge9_result.py`.

### 3.2. Класс случаев, а не один случай

Патч чинит **скругление ребра, конец которого попадает на шов периодической
грани, покрывающей полный период** — цилиндр, конус, сфера, тор, то есть любой
карман, бобышка или отверстие PartDesign. Измерено на трёх независимых стендах:

* минимальная пара «шов далеко / шов на вершине», 4 радиуса × 2 положения:
  было 4 OK + 4 сломанных → стало **8 OK** (`docs/FIX.md`, раздел 1);
* полоса поворота шва 248°…292°, 92 случая: было 68 OK + 24 сломанных → стало
  **92 OK** (там же);
* одиннадцать «катастрофических» радиусов у шва, где объём уходил в
  −506 449 696 мм³: стало **10 из 10 корректных** (там же);
* 247 сгенерированных случаев (куб, цилиндр, конус, сфера, тор; углы на 2/3/4/6/12
  рёбер; ребро, провёрнутое вокруг шва полным оборотом шагом 10°): **0 отличий**
  от стока, то есть вне шва патч не трогает ничего (`docs/REGRESSION.md`, раздел 6).

Что важно понимать про этот класс: **починка и поломка живут в одной строке**.
Оба эффекта — следствие одного и того же безусловного сдвига на период. Значит
«взять починку, а поломку оставить за бортом» можно ровно одним способом:
написать правильную охрану (раздел 6).

## 4. Что рискованно и что неизвестно

Без смягчений.

1. **Две регрессии — это не всё, что может быть сломано.** Из 475 случаев группы
   `blend` исполнено 183; **292 пропущены**, и **все 279 случаев группы
   `chamfer` пропущены**, потому что им нужны модели из репозитория
   `occt-test-data`, который недоступен (`git.dev.opencascade.org` не
   резолвится, зеркал не найдено). Пропущенные случаи — как раз сложные реальные
   тела. Группы `bugs`, `offset`, `feat`, `heal` не запускались вовсе.
2. **`PartDesign::Fillet` на патченом ядре не проверялся.** Всё измерено прямым
   вызовом `BRepFilletAPI_MakeFillet`. Что фича FreeCAD на патченом ядре даст то
   же самое — правдоподобно и не измерено: для этого нужна копия установки
   FreeCAD (2104 МБ) с подменённой DLL.
3. **Деталь одна, ребро одно.** Класс из раздела 3.2 подтверждён синтетикой, а
   не второй реальной деталью.
4. **Границы полосы зависания не найдены.** Известно: r = 0,50 и 0,55 не
   возвращаются, соседние радиусы считаются за 0,19 с. Где полоса начинается и
   кончается — не бисектировано: каждая точка внутри стоит 5 минут.
5. **Предложенная замена охраны — гипотеза.** Она не написана, не собрана, не
   измерена. Больше того, вариант «сдвигать только если точка остаётся внутри
   границ грани» (`docs/REGRESSION.md`, раздел 5) сам требует проверки: в
   измеренной трассе владельца правильный сдвиг даёт u ≈ 6,39 при номинальной
   границе цилиндрической грани 2π ≈ 6,283 — такая охрана рискует отвергнуть
   именно ту починку, ради которой всё затевалось. Сначала измерить границы
   грани, потом выбирать формулировку.
6. **Расхождение, оставленное как есть:** на r = 0,45 старое измерение через
   FreeCAD дало 4599,7393, новое на голом OCCT — 4595,2806. Оба тела невалидны и
   BOP-грязны; совпадения мусора с мусором никто не обещал, но факт записан.
7. **Времена — верхние оценки:** измерялись, когда на машине шла чужая сборка
   (13 процессов `cl.exe`). Разницу «0,19 с против невозврата за 300 с» нагрузкой
   не объяснить, а вот 12/13/30 с на пересборку в спокойной системе могут
   отличаться.
8. **В репозитории работают несколько агентов.** В `occt/` лежит чужая
   незакоммиченная трассировка (раздел 2.6), `install/` не под git. Перед длинной
   работой стоит зафиксировать состояние.

## 5. Стоит ли писать в OCCT и что именно писать

**Да, стоит — но как отчёт о дефекте с воспроизведением, а не как этот патч.**
Отправлять правку, про которую мы сами знаем, что она ломает два случая штатного
набора, нельзя: её отклонят, и правильно сделают.

Два факта, ради которых отчёт имеет ценность.

**(а) Дефект жив в сегодняшнем upstream.** Проверено сегодня, чтением файла из
`master`:

```
$ WebFetch https://raw.githubusercontent.com/Open-Cascade-SAS/OCCT/master/
           src/ModelingAlgorithms/TKFillet/ChFi3d/ChFi3d_Builder_C1.cxx
  вызов в PerformOneCorner: "Yes, guarded by if (onsame)"
  тело ChFi3d_Recale не изменилось: BasisSurface(), IsUPeriodic(), порог 0.5*uper
```

То же в локальных копиях того же файла из 7.9.0 (строка 903) и 8.0.1
(строка 990) — обе содержат `if (onsame)`. За три мажорные версии ни охрана, ни
функция не менялись.

**(б) У этого места есть история, и она объясняет, почему чинить надо
аккуратно.** В том же файле, строки 2422–2469, лежит закомментированный блок:

```cpp
    // offset of parameters if they are not in the same period

    // commented by eap 30 May 2002 occ354
    // the following code may cause trimming a wrong part of periodic surface

//     if (DStr.Surface(Fd->Surf()).Surface()->IsUPeriodic()) { ... сдвиг на 2*pi ... }
```

`occ354` — реальный номер в трекере OCCT. То есть **в 2002 году эту же беду уже
пытались чинить этим же приёмом** — сдвигом параметра на период рядом со швом —
и отключили правку с формулировкой «может обрезать не ту часть периодической
поверхности». Наши две регрессии на теле вращения 270° — буквально то, о чём
предупреждал автор той записи, только в соседней функции. Это превращает отчёт
из «нашли баг» в «нашли баг и знаем, о какую стену уже разбивались».

**Что должно быть в отчёте:**

1. Заголовок: `ChFi3d_Builder::PerformOneCorner` не нормализует параметры
   периодической грани, когда вершина угла лежит на шве, а полоса не в состоянии
   `ChFiDS_OnSame` (`ChFi3d_Builder_C1.cxx:807` в 7.8.1, та же охрана в `master`).
2. Воспроизведение на голом DRAWEXE, без FreeCAD (у нас оно есть на C++; надо
   переписать в полтора десятка строк Tcl — шаг 3 раздела 6).
3. Измеренный симптом: тело **растёт** в объёме (+597,33 мм³ на детали владельца
   при r = 1,0), `BRepAlgoAPI_Check` грязный, при r = 0,5 и 0,55 построение не
   возвращается за 300 с. `isValid()` при этом местами возвращает `true` — то
   есть штатная проверка дефект не ловит.
4. Диагноз с числами: `pfac1.X = 6,176614355`, `pfac2.X = 0,106570952`,
   |du| = 6,070043 при периоде 6,283185 — две точки на разных берегах шва;
   `onsame = false`, поэтому `ChFi3d_Recale` пропускается; окно обрезки,
   переданное пересекателю, не содержит вершину угла.
5. Указание, что сестринская функция `IntersectMoreCorner` (там же, строка 4031 чистого 7.8.1; функция начинается на 3752)
   зовёт `ChFi3d_Recale` **безусловно** и слова `onsame` не содержит вовсе.
6. Честный отчёт о нашей попытке: снятие охраны чинит шов и **ломает**
   `blend/simple/H4` и `blend/buildevol/D6` (270° `revol`) — с числами площадей
   и с диагнозом из раздела 1. Плюс ссылка на `occ354` как исторический контекст.
7. Предложение по направлению: охрана должна опираться на то, замкнута ли **сама
   грань** по периоду (есть ли у неё шов), а не на периодичность базовой
   поверхности после снятия обрезки.

**Куда писать:** GitHub, `Open-Cascade-SAS/OCCT` — issues и pull requests там
включены и живые (проверено сегодня: 146 открытых issue, 57 открытых PR). Трекер
`tracker.dev.opencascade.org` в README тоже указан, но его хост с этой машины не
резолвится.

## 6. Три следующих шага

**Шаг 1 — СДЕЛАН в ночь на 12 сентября, см. `docs/PATCH_V2.md`.** Охрана
написана (`onsame || Bs.IsUClosed() || Bs.IsVClosed()`), критерий приёмки из
этого абзаца взят целиком: `blend` — 181 OK при нуле регрессий (и при нуле
различий вообще), Edge9 — 7 из 7 clean, 247 своих случаев — байт в байт как
сток, каждый набор прогнан дважды. Формулировка задачи, как она стояла:

> **Шаг 1. Написать правильную охрану и измерить её.** Вместо снятия `if (onsame)`
— условие, отличающее «две точки на берегах настоящего шва» от «широкая грань».
Первый кандидат: звать `ChFi3d_Recale`, только когда грань замкнута по u (её
параметрический размах равен периоду, то есть у неё физически есть шов), а не
когда периодична базовая поверхность. Перед этим измерить
`Bs.FirstUParameter()/LastUParameter()` и `BRepTools::UVBounds` на обеих
геометриях — на детали владельца и на 270° `revol` из H4; без этих двух чисел
формулировка охраны будет угадыванием. Цена: правка + 13 с пересборки + два
прогона набора. **Критерий приёмки жёсткий и уже определён: `blend` возвращается
к 181 OK при нуле регрессий, развёртка Edge9 остаётся 7 из 7 clean, а 247
сгенерированных случаев — побайтово как сток.**

*Как это сделано:* приватное дерево `C:/dev/occt-cond`, своё дерево сборки
`build/occt-cond`, три ядра `build/bin-{stock,cond,blunt}`, различающиеся ровно
одним файлом `TKFillet.dll` (остальные 22 DLL побайтово одинаковы). Догадка о
«замкнутости грани» не угадана, а измерена: инструментированное стоковое ядро
напечатало на строке 807 размах грани по U и `IsUClosed` для всех трёх углов
(`docs/PATCH_V2.md`, раздел 1).

*История, как она выглядела на момент написания вердикта:* в `git status`
появились `build-scripts/configure-occt-cond.ps1` и `build-occt-cond.ps1`, и

провален — смотреть `build/occt-cond/build.status` и свежие коммиты.

**Шаг 2 — остаётся главным и единственным серьёзным. Закрыть дыру в покрытии.** Сейчас 292 из 475 случаев `blend` и все 279
`chamfer` пропускаются из-за отсутствия `occt-test-data`. Пока дыра открыта, ни
