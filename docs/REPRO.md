# Воспроизведение дефекта на голом OCCT, без FreeCAD

Этот документ описывает `repro/cpp/seam_fillet.cpp` — программу, которая воспроизводит
дефект скругления у шва **напрямую через `BRepFilletAPI_MakeFillet`**, без FreeCAD,
без Python, без PartDesign.

Дата измерений: 12 сентября 2026 года.
Полный вывод, на который ссылается каждое число ниже: `repro/cpp/seam_fillet_output.txt`.

---

## 0. Зачем это нужно

В `docs/MEASUREMENTS.md` дефект измерен **через FreeCAD 1.1.1**. Этого недостаточно,
чтобы обвинять ядро: между пользователем и `BRepFilletAPI_MakeFillet` стоит целый слой
FreeCAD — `PartDesign::Fillet` сам собирает аргументы, есть обёртка `TopoShape`,
есть healing. Пока измерение идёт через этот слой, остаётся законный вопрос: а не он ли
ломает результат?

Эта программа снимает вопрос. Она вызывает `BRepFilletAPI_MakeFillet` напрямую и
слинкована с ядром, **собранным из исходников** в `C:/dev/seamless/build/occt-release`
(см. `docs/BUILD.md`), а не с DLL из поставки FreeCAD.

**Ответ: дефект воспроизводится. Виновато OCCT, слой FreeCAD ни при чём.**

## 2. Стенд и как в нём двигается шов

Стенд повторяет `repro/python/seamlib.py`: коробка 25 x 25.7184 x 10 мм, цилиндрический
карман радиусом 6.647656 мм и глубиной 13 мм, ось наклонена на 45 градусов вокруг Y и
проходит через точку (25, 12.7, 10) на верхнем переднем ребре коробки. Скругляется прямое
ребро при x = 25, z = 10 длиной 6.370744 мм, уходящее от кармана.

Шов двигается **иначе, чем в Python-версии, и это сделано намеренно**. Цилиндрическая
поверхность периодична по `u`, поэтому обязана нести шов на изо-линии `u = 0`, а где эта
изо-линия лежит — решает `XDirection` у `gp_Ax2`, и больше ничто. Поэтому программа строит
все версии кармана из **одной и той же** точки вершины, с **одной и той же** осью,
**одним и тем же** радиусом и **одной и той же** длиной, меняя только `XDirection`,
повёрнутый на `--rot` градусов вокруг оси:

```cpp
gp_Ax2 PocketAxisFrame(Standard_Real rotDeg)
{
  const gp_Dir axis = PocketAxisDir();
  gp_Dir xdir = ReferenceX();
  if (rotDeg != 0.0) {
    gp_Trsf t;
    t.SetRotation(gp_Ax1(ApexPoint(), axis), rotDeg * PI_ / 180.0);
    xdir = gp_Dir(gp_Vec(xdir).Transformed(t));
  }
  return gp_Ax2(ApexPoint(), axis, xdir);
}
```

Это строже, чем повернуть готовый цилиндр через `gp_Trsf`: преобразование порождает новое
тело, числа которого могут разойтись в последних битах. Здесь же цилиндрическая
поверхность — буквально то же множество точек, просто описанное с другим началом отсчёта
параметра `u`.

Развёртка по `--probe` (раздел 1 файла вывода) показывает, что объём тела не меняется
вообще, а шов ездит:

```
rotDeg   volume          faces  edges  seams  distCurve    distVertex
0.00     5849.473574     8      18     2      11.514078    11.514078
90.00    5849.473573     8      17     2      13.295312    13.295312
180.00   5849.473569     8      18     2      11.514078    11.514078
270.00   5849.473570     8      17     2      0.000000     0.000000
```

При `rot = 270` конец шва садится ровно в конечную вершину скругляемого ребра —
точка (25.0000, 19.3477, 10.0000).

Совпадение с измерениями через FreeCAD точное: там `AngleXU = 0` дало
`dist = 11.514077943` мм, здесь `rot = 0` даёт `11.514078`.

```

  volume(B) = 5849.473570206
  difference = 3.649e-06 mm3

  volume(A - B) = 0.000000000000 mm3

  spine A: length 6.370744000  (25.0000, 19.3477, 10.0000) -> (25.0000, 25.7184, 10.0000)
  spine B: length 6.370744000  (25.0000, 19.3477, 10.0000) -> (25.0000, 25.7184, 10.0000)

  seam endpoint -> spine endpoint: A = 11.514077943 mm, B = 0.000000000 mm
  -> the ONLY difference is the seam: YES
```

Каждое тело режет другое **в ноль** — это одна и та же область пространства, а не просто
равные объёмы. Скругляемое ребро совпадает по длине и по обеим вершинам. Единственное
различие — положение шва.

Заодно программа печатает две pcurve шва прямо из OCCT, без FreeCAD:

```
seam 1: pcurve A Geom2d_Line at u = 6.2832 ; pcurve B Geom2d_Line at u = 0.0000
seam 2: pcurve A Geom2d_Line at u = 0.0000 ; pcurve B Geom2d_Line at u = 6.2832
```

Это ровно тот факт, который был измерен в FreeCAD: одно ребро, одна грань, две `Line2d` —
при `u = 2*pi` и при `u = 0`.

## 4. Главная таблица: пара x четыре радиуса

Каждая строка — **отдельный процесс со своим дедлайном 600 с** (`repro/cpp/run_seam_fillet.sh`).
Зависание здесь — это результат, а не затык: `timeout` убивает процесс, а код возврата 124
записывается как `HANG`.

```
rotDeg   radius   distVtx      status                 valid   volume         removed        analytic     secs     bop
0        0.25     11.514078    OK                     true    5849.388121    +0.085453      0.085448     0.003    clean
0        0.5      11.514078    OK                     true    5849.131723    +0.341850      0.341793     0.003    clean
0        1.0      11.514078    OK                     true    5848.105498    +1.368076      1.367173     0.004    clean
0        2.0      11.514078    OK                     true    5843.990406    +5.483168      5.468693     0.004    clean
270      0.25     0.000000     BROKEN_WRONG_VOLUME    true    5849.420416    +0.053154      0.085448     0.012    DIRTY
270      0.5      0.000000     BROKEN_WRONG_VOLUME    false   4953.892213    +895.581358    0.341793     0.013    DIRTY
270      1.0      0.000000     BROKEN_VOLUME_GREW     false   6224.444835    -374.971265    1.367173     0.010    DIRTY
270      2.0      0.000000     BROKEN_VOLUME_GREW     false   6193.313396    -343.839826    5.468693     0.011    DIRTY
```

`removed` — это `volume(база) - volume(после скругления)`. **Отрицательное значение
означает, что скругление ДОБАВИЛО материал**, чего никакое скругление сделать не может.

Читается так:

* **Шов далеко (11.51 мм) — все четыре радиуса верны.** Снятый объём сходится с
  аналитическим `(1 - pi/4) * r^2 * L` с точностью около 0.07 %: 0.085453 против 0.085448,
  1.368076 против 1.367173. BOP-проверка чиста во всех четырёх.
* **Шов на вершине (0 мм) — все четыре радиуса испорчены**, и по-разному:
  * `r = 0.25`: `isValid() = true`, но снято 0.053154 вместо 0.085448 — **тихий отказ**;
  * `r = 0.5`: снято 895.58 мм³ вместо 0.34 — тело срезано почти на шестую часть;
  * `r = 1.0`: объём **вырос** на 374.97 мм³;
  * `r = 2.0`: объём **вырос** на 343.84 мм³.

Сопоставление с FreeCAD: там на `r = 1.0` объём вырос на 356.4531 мм³, здесь — на
374.971265. Разница только в том, какая именно фаза шва попадает на вершину: FreeCAD
отсчитывает `AngleXU` от оси X эскиза, а эта программа — от `XDirection` у `gp_Ax2`.
Качественно и по порядку величины это один и тот же отказ.

### Что говорят сами проверки

```
r = 0.25: valid true   BOP DIRTY SelfIntersect x40 TooSmallEdge x14         faces 8 -> 9, edges 17 -> 21
r = 0.5 : valid FALSE  BOP DIRTY NotValid x1 SelfIntersect x91 TooSmallEdge x14   faces 8 -> 9, edges 17 -> 21
r = 1.0 : valid FALSE  BOP DIRTY NotValid x1 SelfIntersect x24 TooSmallEdge x10   faces 8 -> 8, edges 17 -> 18
r = 2.0 : valid FALSE  BOP DIRTY NotValid x1 SelfIntersect x24 TooSmallEdge x10   faces 8 -> 8, edges 17 -> 18
```

При `r = 1.0` и `r = 2.0` число граней **не изменилось**: 8 было, 8 стало. Скругление не
добавило ни одной грани — оно не построило скругление вообще, а вернуло изувеченное тело.

Строка `r = 0.25` — подтверждение того, ради чего в задании отдельно оговорена проверка
валидности: `BRepCheck_Analyzer` (то, что вызывает `Shape.isValid()` во FreeCAD)
говорит `true` о теле, у которого BOP-проверка находит 40 самопересечений.
**`isValid()` в этой области верить нельзя, верить можно только `BRepAlgoAPI_Check`.**
Теперь это измерено и на голом OCCT, не только через FreeCAD.

## 5. Полоса опасности: порог — примерно один радиус скругления

Развёртка по `rot` от 248 до 292 градусов, четыре радиуса, всего 70 дополнительных
процессов (разделы 4, 4b файла вывода). Сведение:

```
radius   max_broken     min_intact     max_broken/r
0.25     0.164077       0.328122       0.656
0.5      0.328122       0.655995       0.656
1.0      0.983368       1.309993       0.983
2.0      1.960011       2.282913       0.980
```

`max_broken` — наибольшее расстояние «конец шва — конец ребра», при котором результат ещё
испорчен; `min_intact` — наименьшее, при котором он уже верен.

**Правило: скругление радиуса `r` ломается, пока конец шва ближе примерно `r` миллиметров
к концу скругляемого ребра.** Отношение `max_broken / r` = 0.656, 0.656, 0.983, 0.980.

Это то же самое правило, что было выведено на измерениях через FreeCAD
(`docs/MEASUREMENTS.md`, раздел 3.5), где отношения вышли 0.656, 0.984, 0.983, 0.980.
Два независимых пути измерения — через FreeCAD и напрямую через OCCT — дали один и тот же
порог.

Полоса несимметрична относительно точного попадания шва на вершину, и формы отказа по обе
стороны разные. Слева от 270 (углы 264–269) чаще встречается громкий отказ — `valid = false`
и выросший объём; справа (углы 274–282) — тихий: `valid = true`, но снято вдвое больше
положенного, например при `r = 1.0` и `rot = 276` снято 2.251602 мм³ вместо 1.367173.
Тихий отказ опаснее: такое тело выглядит исправным.

## 7. Зависание НЕ воспроизвелось — и это тоже измерение

Всего выполнено **89 случаев**, каждый отдельным процессом под своим дедлайном
(600 с в разделах 3 и 5, 300 с в разделах 4 и 4b).

```
HANG count: 0
Slowest single case: 0.022 s
```

Ни один случай не приблизился к дедлайну: самый медленный занял 22 миллисекунды из 600
секунд. Полоса зависания, измеренная на реальной детали владельца (радиусы 0.5 и 0.55,
9.2 минуты без завершения), на минимальном стенде **не воспроизводится**.

Это честная граница того, что здесь доказано. Порча результата воспроизводится полностью;
зависание — нет. Скорее всего для зависания нужна более сложная топология реальной детали
(несколько скруглений подряд, тороидальные грани от предыдущих скруглений — см. раздел 4.2
в `docs/MEASUREMENTS.md`). Отдельный стенд под зависание ещё не построен.

Механизм дедлайна при этом не «не пригодился» — он проверен: в первом запуске все восемь
случаев вернули `EXIT_127`, и таблица честно это показала, вместо того чтобы промолчать.
Причина была в том, что Git Bash не переводит запись вида `C:/...` внутри `PATH`, и
загрузчик не находил DLL. Исправлено в `run_seam_fillet.sh`, там же оставлен комментарий.

## 8. Как перезапустить

```bash
# 1. собрать (cl.exe вызывается напрямую, без vcvars и без cmd.exe)
powershell -NoProfile -ExecutionPolicy Bypass -File build-scripts/build-seam-fillet.ps1

# 2. главная таблица: пара x четыре радиуса, по процессу на случай, дедлайн 600 с
bash repro/cpp/run_seam_fillet.sh 600

# 3. отдельные режимы
export PATH="/c/dev/seamless/build/occt-release/win64/vc14/bin:$PATH"
cd /c/dev/seamless/build/seam-fillet
./seam_fillet.exe --probe --rot-from 0 --rot-to 350 --rot-step 10   # где шов
./seam_fillet.exe --identical 0 270                                 # тела одинаковы
./seam_fillet.exe --case --rot 270 --radius 1.0 --brep bad.brep     # один случай
```

`--brep` выгружает получившееся тело в формате BREP — единственный формат, который это
ядро читает и пишет (STEP/IGES/STL выключены, см. `docs/BUILD.md`).

Переменные окружения `ROTS`, `RADII`, `LOGDIR` задают свою матрицу:

```bash
ROTS="270" RADII="0.1 0.55 3.0" LOGDIR=/tmp/mylogs bash repro/cpp/run_seam_fillet.sh 600
```

**Важно про PATH.** Каталог с DLL обязан быть в `PATH` в POSIX-виде
(`/c/dev/...`), а не в виде `C:/dev/...`: Git Bash второй не переводит, и программа
падает с кодом 127 ещё до `main()`.

## 9. Что из этого следует

1. **Дефект в OCCT, не во FreeCAD.** `BRepFilletAPI_MakeFillet`, вызванный напрямую,
   с ядром, собранным из исходников 7.8.1, на теле, построенном тремя вызовами
   `BRepPrimAPI` и `BRepAlgoAPI_Cut`, возвращает испорченный результат. Слоя FreeCAD
   в этой цепочке нет вовсе. Искать обходной путь внутри FreeCAD бессмысленно —
   чинить или обходить надо на уровне ядра.

2. **`IsDone()` не значит ничего.** Во всех 89 случаях, включая тот, где объём получился
   равным минус полумиллиарду, `Build()` отработал и `IsDone()` вернул `true`.

3. **`isValid()` не значит почти ничего.** Измерено на голом OCCT: `BRepCheck_Analyzer`
   говорит `true` о теле с 40 самопересечениями по `BRepAlgoAPI_Check`. Проверять надо
   `BRepAlgoAPI_Check`, а лучше — ещё и объём против ожидаемого.

4. **Порог известен и прост:** скругление радиуса `r` небезопасно, пока конец шва ближе
   примерно `r` мм к концу скругляемого ребра. Это даёт прямое правило для будущего
   приложения: перед скруглением найти швы (`BRep_Tool::IsClosed(edge, face)`), измерить
   расстояние до вершин ребра и либо отказаться, либо сдвинуть шов.

5. **Самый дешёвый обход уже известен** и не требует трогать ядро: шва можно просто не
   создавать. Грань, покрывающая 359 градусов вместо 360, шва не имеет
   (`docs/MEASUREMENTS.md`, разделы 1.4 и 6). Проверка этого обхода на голом OCCT —
   следующая работа; здесь она не делалась.

`repro/cpp/seam_fillet_repro.cpp` — отдельная, более ранняя программа другой группы;
она слинкована с DLL из поставки FreeCAD через сгенерированные import-библиотеки.
Эта программа независима от неё: своё ядро, свой способ двигать шов, свой дедлайн
на каждый случай. То, что два разных пути дали один и тот же порог, — дополнительное
подтверждение, а не дублирование.
